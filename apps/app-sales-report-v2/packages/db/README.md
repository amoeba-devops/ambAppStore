# @v2/db — Drizzle Schema + Migrations

Source of truth for the FIRGI Sales Report v2 database schema. All
business logic queries go through `import { db, schema, withEnt } from '@v2/db'`.

## Migration workflow (current standard)

```bash
# 1. Edit a schema file under src/schema/*.schema.ts
# 2. Generate the migration SQL from the diff
npm run db:generate -- --name=add_my_column

# 3. Review the generated SQL in migrations/NNNN_add_my_column.sql
# 4. Apply to the configured DATABASE_URL
npm run db:migrate
```

Both scripts use `dotenv-cli` so they pick up `DATABASE_URL` from
`../../.env`. Never hand-edit `migrations/meta/_journal.json` or
`migrations/meta/*_snapshot.json` — they're drizzle-kit's tracking state.

## Historical drift — migrations 0006–0017

**Read this before touching `meta/`.**

Migrations `0000_great_swarm.sql` through `0005_add_period_snapshots.sql`
were generated by `drizzle-kit generate` and are properly recorded in
`meta/_journal.json` + per-step snapshots.

Migrations `0006_add_archive_files.sql` through
`0017_drop_psp_fx_rate_snapshot.sql` were applied **outside** drizzle-kit —
authored by hand and applied to the dev/staging/prod databases via raw
`ALTER TABLE` calls in Node scripts during the rapid-iteration phase. As
a result:

- The SQL files exist on disk and reflect what's in the deployed DBs.
- `meta/_journal.json` still only references entries 0–5.
- `drizzle-kit generate` would now diff its last-known snapshot (0005)
  against the current `src/schema/*.schema.ts` and produce a huge
  catch-up migration that re-creates already-applied changes. **Do not
  run an unreviewed `db:generate` until this is reconciled.**

If you need to add a new migration today, the safe path is:

1. Run `npm run db:generate -- --name=...`.
2. **Open the generated SQL** and delete every statement that recreates
   existing columns/tables. Keep only the lines for your actual change.
3. Verify against a fresh Neon dev branch before applying to staging.

### Eventual reconciliation (deferred)

Either:
- **Squash to a baseline**: drop `migrations/` + `meta/`, run
  `db:generate -- --name=0000_baseline` against current schema, then
  insert that single hash into `__drizzle_migrations__` on every
  existing DB so drizzle-kit treats the schema as already-applied. Loses
  historical SQL but unifies the source of truth.
- **Backfill**: manually author `meta/000N_snapshot.json` for each of
  0006–0017 to reflect intermediate schema states. Tedious; high risk
  of typos; deferred until someone owns it.

Pick the squash route the next time you have a maintenance window — the
backfill is not worth the effort for a single-client deployment.

## Conventions

- Naming: `{prefix}_{name}` columns, `sal_*` tables — per root CLAUDE.md.
- Multi-tenancy: every business table carries `ent_id CHAR(36) NOT NULL`.
  Queries MUST wrap with `withEnt(table.entId, user.entId)` — there is no
  row-level security at the DB layer; the helper is the enforcement point.
- Soft delete: `{prefix}_deleted_at TIMESTAMPTZ NULL`. Reads should filter
  `IS NULL`.
- Unique partial indexes ignore soft-deleted rows (see `uniq_sal_pcs_ent_sku`
  for the pattern).

## Adding a versioned business field

Pattern established by `sal_prime_cost_versions` / `sal_selling_price_versions`
/ `sal_listing_price_versions`:

1. Master table holds the latest value (cached) + flags.
2. Sister `_versions` table stores `effective_from DATE NOT NULL` rows.
3. Calculator scans versions DESC by `effective_from` and picks the first
   with `effective_from <= orderDate`.
4. Auto-version on every change (CSV import + UI Edit) so the timeline
   is always complete.

Don't store the price directly in `_versions` AND in the master without
keeping them in sync — the master is the cache, version table is the
ledger.
