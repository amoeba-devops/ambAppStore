# HS Code Manager — 개념 및 설계 문서

> 원본: 「2026.04.02 HS CODE 처리 방식」 매뉴얼
> 작성 범위: ① 시스템 기능 명세 → ② 에스컬레이션·피드백 정책 → ③ ERP DB 스키마 → ④ 정보수집 폼 설계
> 설계 기조: 기존 매뉴얼의 4단계 파이프라인(수집 → 판단 → 검증 → 응대/기록)을 시스템에 그대로 매핑하되, 누락된 "피드백 루프"와 "에스컬레이션 룰"을 1급 시민으로 끌어올린다.

## 1. 시스템·앱 기능 명세

### 1.1 도메인 개념과 핵심 엔티티

이 앱이 다루는 세계는 단순하다. 고객사가 어떤 **물품(Item)**에 대해 **문의(Inquiry)**를 보내면, 담당자가 정보를 수집해 **HS코드 후보(Classification Candidate)**를 산출하고, 그중 하나를 **확정 분류(Confirmed Classification)**로 채택해 응대한다. 확정 분류는 시간이 흐른 뒤 실제 통관 결과(추징 발생 여부, 샘플 분석 결과)에 의해 **검증(Verification)**된다. 이 검증 결과가 다시 분류 로직에 피드백되어야 시스템이 학습한다.

따라서 이 앱의 일급 엔티티는 다섯 가지다.

| 엔티티 | 의미 | 라이프사이클 |
|---|---|---|
| Inquiry | 고객사로부터 들어온 문의 1건 | 접수 → 수집중 → 분류중 → 검증중 → 응대완료 → (사후) 검증완료/추징발생 |
| Item | 문의 대상 물품 (재사용 가능) | 신규등록 → 분류이력 누적 |
| Classification | HS코드 분류 후보·확정값 | 후보제안 → 채택 → (사후) 확정 또는 정정 |
| ExpertReview | 전문가 크로스체크 기록 | 요청 → 검토중 → 회신완료 |
| VerificationEvent | 통관 후 검증·추징 이벤트 | 발생 → 사유분석 → 분류기준업데이트 |

이 다섯 엔티티가 서로를 참조하는 구조는 다음과 같다. **하나의 Inquiry는 하나의 Item을 가리키고**, **하나의 Item은 여러 Classification을 시간 순서로 누적**한다(같은 물품도 규제·세율 변동으로 코드가 달라질 수 있다). **Classification은 채택 직후 ExpertReview를 0~1건 가질 수 있고**, **VerificationEvent는 Classification에 사후적으로 매달린다**.

### 1.2 기능 모듈 (4단계 매뉴얼 → 4개 모듈)

매뉴얼의 4단계를 그대로 모듈로 변환한다. 각 모듈은 책임이 분리되어 있어야 하며, 단계 간 인터페이스(전달 데이터)가 명확해야 한다.

**M1. 정보 수집 모듈 (Intake)**
역할은 "3대 핵심 정보(품명·용도, 성분·스펙, 사진·도면)를 누락 없이 수집"하는 것이다. 핵심 설계 포인트는 *품목군별로 폼이 동적으로 바뀐다는 것*이다. 화학물질을 등록하면 MSDS 업로드 필드가 활성화되고, 철강·기계를 등록하면 두께·재질·작동원리 필드가 활성화된다. 이 동적 폼의 스키마는 §4에서 상세 설계한다. 산출물은 `Inquiry` 1건과 그에 묶인 `Item` 마스터 데이터다.

**M2. HS코드 조회·리스크 검토 모듈 (Classify)**
역할은 "후보 HS코드를 도출하고 보수적 선택 룰에 따라 1순위를 제안"하는 것이다. 외부 데이터 소스 두 곳을 통합해야 한다 — 한국 관세청 HS 조회와 베트남 *BIEU THUE XNK 2026*. 또한 FTA C/O 혜택세율을 별도로 계산해서 "기본세율 vs 협정세율" 비교 뷰를 제공한다. 보수적 선택 룰(§2.2에서 정책으로 정형화)에 따라 시스템이 1순위 코드를 자동 제안하되, 담당자가 오버라이드할 수 있어야 한다.

**M3. 전문가 크로스체크 모듈 (Expert Review)**
역할은 "에스컬레이션 룰에 부합하는 건을 자동으로 적절한 전문가에게 라우팅하고, 회신을 받아 반영"하는 것이다. 누가 어디로 가는지의 기준은 §2.1에서 명시한다. 이 모듈은 **차단형(blocking)**으로 동작한다 — 라우팅된 건은 전문가 회신 전까지 M4로 진행되지 않는다.

**M4. 응대·기록 모듈 (Respond & Archive)**
역할은 "확정된 추천 코드·관세율·수입요건을 고객 대응 양식으로 출력하고, ERP DB에 영속화"하는 것이다. 출력 양식은 채널별로 다르게 렌더링한다(이메일, 카카오톡, 사내 메신저). 영속화 시점에 `Item`과 `Classification`이 ERP에 누적되어, 다음 동일 품목 문의가 들어왔을 때 M1에서 자동 매칭된다.

### 1.3 횡단 관심사 (Cross-cutting concerns)

네 모듈을 가로지르는 두 개의 축이 있다.

첫째, **사후 검증 루프(Verification Loop)**는 M4 이후에도 끝나지 않고, 통관 완료/샘플 분석/세관 추징 이벤트를 받아 해당 `Classification`의 신뢰도를 갱신한다. 이는 매뉴얼에 명시되지 않은 부분이지만, ERP 축적이 의미 있으려면 반드시 필요하다. §2.3에서 정책으로 정의한다.

둘째, **신뢰도 점수(Confidence Score)**는 모든 Classification에 0~1 사이 값으로 부여된다. 점수의 입력 변수는 (a) 정보 수집 완성도, (b) 후보 코드 간 세율 격차, (c) 전문가 검토 여부, (d) 동일 품목의 과거 검증 이력이다. 이 점수가 임계값 미만이면 자동으로 M3 에스컬레이션이 발동된다.

## 2. 에스컬레이션·피드백 정책

원본 매뉴얼에서 가장 모호하게 처리된 영역이다. 시스템 설계 관점에서 이 부분을 명문화하지 않으면 자동화의 절반은 사람의 직관에 묶이게 된다.

### 2.1 전문가 라우팅 룰 (Mr. Nguyen vs Ms. Hau)

매뉴얼은 두 명의 이름만 등장시키고 "어떤 건이 누구에게 가는지"를 명시하지 않았다. 이를 다음과 같이 정형화한다.

| 조건 | 라우팅 대상 | 근거 |
|---|---|---|
| 베트남 현지 통관·세관 절차, 라이선스 요건 해석 | Mr. Nguyen (현지 통관사) | 현지 규제 권위자 |
| 사내 분류 정책, 과거 사례 일관성, FTA 원산지 판정 | Ms. Hau (내부 전문가) | 내부 지식·이력 보유자 |
| 위 두 영역 모두 걸리는 경우 | 병렬 라우팅 (둘 다 회신 필요) | 양 영역의 합치 필요 |

라우팅을 자동화하려면, M1에서 수집된 정보에 **"규제 플래그"**가 부여되어야 한다. 예를 들어 화학물질이면 베트남 화학물질법 적용 여부 → Mr. Nguyen, FTA 원산지증명서 발급 검토 필요 → Ms. Hau. 이 플래그는 M2의 후보 코드 도출 과정에서 자동 부착된다.

### 2.2 보수적 세율 선택 룰의 정형화

매뉴얼은 "0%와 3% 사이에서 모호하면 3%로"라는 예시 한 줄로 처리했다. 이를 정책으로 일반화한다.

원칙은 *"후보 간 세율 격차가 클수록 보수적으로, 작을수록 합리적 최저로"* 이다. 구체적 임계값은 다음과 같이 둔다.

- 후보 코드 간 세율 격차가 **3%p 이상**: 높은 세율 채택, 사후 샘플 분석 의무화
- 격차가 **1~3%p**: 높은 세율 채택, 샘플 분석 권고
- 격차가 **1%p 미만**: 낮은 세율 채택 가능, 단 신뢰도 점수가 0.8 이상일 때만

이 임계값은 운영 데이터를 누적해 6개월 단위로 재교정한다. 추징 발생률이 임계 미만(예: <2%)이면 더 공격적으로, 초과하면 더 보수적으로.

### 2.3 사후 검증 피드백 룰

매뉴얼에 빠져 있던 가장 큰 구멍이다. 통관 후 발생하는 세 가지 이벤트를 명시적으로 모델링한다.

첫째, **샘플 분석 결과 회신**. 분석 결과가 채택 코드와 일치하면 해당 `Classification`의 신뢰도를 +0.2 가산하고, 불일치하면 즉시 정정 분류를 등록하면서 원본을 "Superseded(대체됨)" 상태로 전환한다. 동일 품목의 과거 모든 분류를 검토 대상으로 자동 표시한다.

둘째, **세관 추징 발생**. 추징이 발생하면 해당 분류는 즉시 "Disputed(분쟁)" 상태로 전환되고, M3 에스컬레이션이 자동 발동된다. 동시에 *동일 분류 코드를 사용한 다른 모든 Item*을 검색해 "재검토 후보"로 큐에 적재한다 — 한 건의 추징이 같은 패턴의 추징을 예고할 수 있기 때문이다.

셋째, **세관 더블체크 결과**. 사전에 세관에 직접 확인한 건은 신뢰도를 +0.3 가산하고, 해당 코드를 "Sealed(확정)" 상태로 잠금 — 이후 같은 품목 문의 시 분류 단계를 스킵한다.

이 세 이벤트는 ERP DB에 `VerificationEvent` 레코드로 저장되며, 월간 추징률·정정률·세관확인률 KPI 대시보드의 입력이 된다.

### 2.4 에스컬레이션 발동 트리거

다음 중 하나라도 해당되면 M3 전문가 크로스체크가 자동 발동된다.

(a) 신뢰도 점수가 0.6 미만, (b) 후보 코드가 3개 이상으로 분기, (c) 베트남 수입금지·제한 품목 키워드와 매칭, (d) 과거 동일 품목에서 추징 이력 존재, (e) 고객사가 명시적 요청, (f) 거래 금액이 기준선(예: USD 50,000) 초과.

## 3. ERP DB 스키마 설계

§1에서 정의한 5개 엔티티를 관계형 스키마로 풀어낸다. 설계 원칙은 *"분류는 시간에 따라 변할 수 있고, Item은 영속한다"* 이다.

### 3.1 핵심 테이블 구조

**Item (물품 마스터)** — 한 번 등록되면 영구 식별자를 가진다. 같은 물품 재문의 시 즉시 매칭되어야 하므로 `name_normalized`, `composition_hash`, `usage_normalized` 같은 정규화 컬럼이 필요하다. 컬럼 구성은 다음과 같다.

```
item_id (PK)
name (raw)
name_normalized
category (chemical | steel_mech | equipment | other)
usage_description
composition_hash         -- MSDS 정규화 해시 (chemical only)
spec_attributes (JSON)   -- 카테고리별 가변 스펙
created_at, updated_at
```

**Inquiry (문의)** — 1건의 고객사 문의. 같은 Item에 대한 문의가 여러 번 들어올 수 있다.

```
inquiry_id (PK)
customer_id (FK)
item_id (FK)
status (intake | classifying | reviewing | responded | verified | disputed)
intake_completeness_score (0..1)
created_at, responded_at
```

**Classification (분류)** — 핵심 테이블. Item에 대한 시점별 분류 기록.

```
classification_id (PK)
item_id (FK)
inquiry_id (FK)               -- 어떤 문의에서 채택되었는지
hs_code (string)
basic_tariff_rate (decimal)
fta_tariff_rate (decimal, nullable)
import_requirements (JSON)    -- 라이선스·규제 요구사항
confidence_score (0..1)
status (proposed | adopted | sealed | superseded | disputed)
selection_rationale (text)    -- 왜 이 코드를 선택했는지
adopted_at, superseded_at
superseded_by (FK self-ref, nullable)
```

**ClassificationCandidate (후보 코드, 채택 여부 무관)** — Classification에 1:N로 매달리는 후보들. 사후 분석에 필수다.

```
candidate_id (PK)
classification_id (FK)
hs_code
tariff_rate
source (kr_customs | vn_bieu_thue | manual)
ranking
```

**ExpertReview (전문가 크로스체크)**

```
review_id (PK)
classification_id (FK)
expert_role (vn_customs_broker | internal_expert)
expert_name (Mr. Nguyen | Ms. Hau | other)
trigger_reason (enum)
requested_at, responded_at
verdict (approve | revise | reject)
notes
```

**VerificationEvent (사후 검증)** — Classification에 시간 순으로 매달림.

```
event_id (PK)
classification_id (FK)
event_type (sample_analysis | customs_seizure | customs_double_check)
event_date
result (match | mismatch | confirmed)
confidence_delta (decimal)
follow_up_actions (JSON)      -- 자동 생성된 후속 작업 (예: 재검토 큐 적재)
```

### 3.2 인덱스·검색 전략

ERP의 가치는 "동일 품목 재문의 시 즉시 대응"에서 나온다. 따라서 다음 세 종류의 검색이 빨라야 한다.

첫째, *품명/용도 기반 fuzzy 매칭* — `name_normalized`에 trigram 인덱스 또는 임베딩 벡터 인덱스. 둘째, *HS코드 기반 역방향 검색*("이 코드를 사용한 모든 Item") — `hs_code` 인덱스. 셋째, *추징 이력 검색* — `VerificationEvent.event_type='customs_seizure'` 부분 인덱스.

### 3.3 시간 모델: 왜 Classification을 immutable에 가깝게 두는가

`Classification` 테이블은 한 번 `adopted` 상태가 되면 거의 변경하지 않는다. 정정이 필요하면 새 레코드를 만들고 기존 레코드를 `superseded` 처리한다. 이는 두 가지를 보장한다 — (1) 과거 응대의 재현 가능성(고객사가 "그때 너희가 뭐라고 했냐"고 물었을 때 정확히 답할 수 있어야 한다), (2) 추징 발생 시 책임 추적성. 이는 회계의 분개와 같은 원칙이다.

## 4. 정보수집용 체크리스트·폼 설계

M1(Intake)의 동적 폼을 구체화한다. 핵심은 *"공통 필드 + 카테고리별 분기 필드"*의 2단 구조다.

### 4.1 공통 필드 (모든 품목 공통)

폼 진입 시 우선 다음 4개 필드를 받는다. 이 정보가 카테고리 분기를 결정한다.

1. **품명(원어/한글/영문)** — 정확한 상품명. 자유 텍스트지만 등록 직후 정규화·매칭 시도.
2. **카테고리 선택** — `chemical | steel_mechanical | equipment | other` 중 택1. 이 선택이 다음 단계의 폼을 결정.
3. **용도 설명** — 어디에 사용되는 물건인지 서술형. 최소 길이 30자.
4. **사진/도면 업로드** — 1장 이상 필수. 유효 포맷 jpg, png, pdf.

이 4개가 채워지면 `intake_completeness_score`의 기본 점수 0.4가 부여된다. 카테고리별 분기 필드가 추가로 채워지면 0.4 → 1.0까지 가산된다.

### 4.2 카테고리별 분기 필드

**A. 화학물질(chemical)**
필수 — MSDS 파일 업로드, 주요 성분 3개 이상(CAS 번호 + 함량 %), CAS 합산 함량 100% ±5% 검증. 선택 — UN 번호, 위험물 분류, pH, 인화점.
체크리스트적 표현: "MSDS에 CAS 번호와 함량이 명시되어 있는가? / 베트남 수입제한 화학물질 목록에 해당 CAS가 있는가?(자동 조회)"

**B. 철강·기계류(steel_mechanical)**
필수 — 재질(예: SS400, SUS304), 두께·치수, 작동 원리 또는 가공 형태(예: 압연/단조/주조). 선택 — 표면 처리, 합금 함량, 인장강도.
체크리스트적 표현: "두께가 명시되어 있는가? / 재질이 합금인 경우 주요 합금 원소와 함량이 명시되어 있는가?"

**C. 설비(equipment)**
필수 — 명판(Nameplate) 사진, 작동 방식 설명, 주요 구성품 목록, 정격 전력/용량. 선택 — 제조사·모델, 자동/수동 여부, 산업 용도.
체크리스트적 표현: "명판이 식별 가능한 해상도로 촬영되었는가? / 구성품 중 별도 HS코드가 적용될 가능성이 있는 항목이 있는가?"

**D. 기타(other)**
필수 — 자유 서술 + 첨부 자료. 자동 라우팅 — 이 카테고리는 M3 에스컬레이션을 자동 발동(전문가가 카테고리를 재분류).

### 4.3 완성도 점수 계산식 (개념)

`intake_completeness_score`는 다음 가중치로 계산한다.

- 공통 4필드 모두 채움: 0.4
- 카테고리 필수 필드 모두 채움: +0.3
- 카테고리 선택 필드 채움 비율: +0~0.2
- 사진/도면이 2장 이상 또는 명판 사진 포함: +0.1

이 점수가 0.7 미만이면 분류 단계로 진행할 수 없도록 차단(soft block, 사용자가 강제 진행 시 사유 기록).

### 4.4 동일 품목 자동 매칭 흐름

폼에서 "품명 + 카테고리"가 입력되는 즉시 ERP DB에서 후보 매칭을 시도한다. 매칭 결과가 신뢰도 0.85 이상이면 *"이 물품은 과거 [HS코드]로 분류되었습니다(횟수: N건, 마지막 분류일: YYYY-MM-DD). 동일 분류로 진행하시겠습니까?"* 라는 다이얼로그를 띄운다. 사용자가 "예"를 선택하면 정보 수집을 스킵하고 M4(응대)로 직행한다. 단, 마지막 분류일이 12개월을 초과한 경우 *세율·규제 변동 가능성 경고*를 함께 표시한다.

## 5. 통합 흐름 (요약)

지금까지의 네 영역을 하나의 흐름으로 연결하면 다음과 같다.

고객 문의 → **M1 Intake**: 카테고리 분기 폼으로 공통+가변 필드 수집, 동일 품목 매칭 시도, `intake_completeness_score` 산출 → **M2 Classify**: 한국 관세청·베트남 BIEU THUE XNK 2026·FTA C/O 데이터를 통합해 후보 도출, 보수적 선택 룰 적용, `confidence_score` 산출 → **에스컬레이션 게이트**: 신뢰도·후보 분기·과거 추징·금액 임계 등 6개 트리거 검사 → 해당 시 **M3 Expert Review**: 베트남 현지(Mr. Nguyen)/내부(Ms. Hau)/병렬 라우팅 → **M4 Respond & Archive**: 채널별 응대 양식 출력, ERP에 `Item`/`Classification` 영속화 → **사후 검증 루프**: 샘플 분석/추징/세관 확인 이벤트를 `VerificationEvent`로 누적, 신뢰도 갱신, 동일 코드 사용 다른 Item 재검토 큐 적재 → 6개월 단위로 보수적 룰 임계값 재교정.

이 흐름의 본질은 **사람이 했던 4단계 절차를 그대로 두되, 그 위에 "신뢰도 점수"와 "검증 루프"라는 두 개의 메타 레이어를 얹는 것**이다. 매뉴얼은 사람의 판단을 적시에 모이게 했지만, 시스템은 그 판단을 데이터로 누적해 다음 판단을 더 빠르고 정확하게 만들어야 한다.
