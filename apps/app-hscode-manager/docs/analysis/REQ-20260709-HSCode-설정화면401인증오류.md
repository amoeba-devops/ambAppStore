# 요구사항분석서 — HS Code Manager 설정(admin) 화면 401 인증 오류

- **문서 ID**: REQ-20260709-HSCode-설정화면401인증오류
- **작성일**: 2026-07-09
- **대상 앱**: HS Code Manager (`/app-hscode`)
- **유형**: 버그 수정 / 인증 정합성
- **관련 증상**:
  - 화면: `https://stg-apps.amoeba.site/app-hscode/admin`
  - `GET /app-hscode/api/v1/admin/settings/AI` → **HTTP 401 (Unauthorized)**
  - `GET /app-hscode/api/v1/reference/imports` → **HTTP 401 (Unauthorized)**
  - **특이점**: 화면 우하단 디버그 패널에 **AMA 유저 정보가 정상 표기**됨(= 토큰이 존재·디코드됨)
- **선행 문서**: [`REQ-20260708-HSCode-AMA-SSO토큰연동`](../../../../docs/analysis/REQ-20260708-HSCode-AMA-SSO토큰연동.md) — 프론트 SSO 토큰 **수신 로직 부재**(토큰 아예 없음) 해결 건. **본 건은 그 후속으로, 토큰이 존재함에도 발생하는 별개 원인**이다.

## 1. 요구사항 요약

| # | 요구사항 | 유형 |
|---|----------|------|
| R1 | 설정(admin) 화면 진입 시 `GET /admin/settings/AI`·`GET /reference/imports`가 401 없이 정상 응답한다 | 버그/필수 |
| R2 | 401의 근본 원인(토큰 서명 검증 실패)을 규명한다 — **토큰 서명 주체(AMA 환경)와 BFF `JWT_SECRET` 정합성** 확인 | 버그/필수 |
| R3 | 세션 도중 토큰 만료 시 무한 401 대신 재인증 유도/명확한 안내를 제공한다 | 기능 |
| R4 | (견고성) `ent_id`가 비-UUID일 때 발생하는 Postgres `uuid` 캐스트 500을 방어한다 | 비기능/견고성 |
| R5 | 라이브 토큰(`exp`·`scope`·서명 주체) 진단 절차를 디버그 패널 기반으로 표준화한다 | 비기능/운영 |

> **핵심**: 이번 401은 "특정 엔드포인트(설정/참조) 고유 결함"도, "토큰 미첨부"도 아니다. **디버그 패널에 유저가 뜨는데 401 = 토큰이 첨부되긴 하나, 전역 `JwtAuthGuard`(passport-jwt)의 서명 검증을 통과하지 못함**을 의미한다. 서명 검증 실패의 유력 원인은 **토큰을 서명한 AMA의 `JWT_SECRET`이 스테이징 BFF의 `JWT_SECRET`과 불일치(교차환경 토큰)** 또는 **토큰 만료**다.

## 2. AS-IS 현황 분석

### 2.1 인증 파이프라인 (검증된 동작)

| 계층 | 파일 | 동작 | 실패 시 HTTP |
|------|------|------|--------------|
| 전역 JWT 가드 | `backend/src/app.module.ts:61` (`{ provide: APP_GUARD, useClass: JwtAuthGuard }`) | 모든 라우트에 전역 적용. `@Public()`만 해제 | — |
| 서명/만료 검증 | `backend/src/auth/jwt.strategy.ts:9-14` | `ExtractJwt.fromAuthHeaderAsBearerToken()`, `secretOrKey: process.env.JWT_SECRET`, `ignoreExpiration:false` | **401** (미첨부/서명불일치/만료) |
| ent_id 격리 | `backend/src/auth/guards/entity-scope.guard.ts` | `@Auth()`/`@AdminOnly()` 하위. `user.entityId` 없으면 차단 | 403 |
| 역할 검사 | `backend/src/auth/guards/role.guard.ts` (`ADMIN_ROLES=['ADMIN','MASTER','SUPER_ADMIN']`) | `@AdminOnly()` 전용 | 403 |

**핵심 논리**: `EntityScopeGuard`·`RoleGuard`는 **403**만 던진다. 따라서 **401은 반드시 `jwt.strategy` 서명 검증 단계에서 발생**하며, 이는 역할/엔티티와 무관한 전역 문제다. → 이 세션의 토큰은 (해당 화면의 모든 호출은 물론) **모든 보호 엔드포인트에서 동일하게 401**이 된다.

### 2.2 문제 엔드포인트 (설정/참조는 죄가 없음)

| 엔드포인트 | 파일 | 데코레이터 |
|-----------|------|-----------|
| `GET /admin/settings/:category` | `backend/src/domain/admin-settings/controller/admin-settings.controller.ts` | `@AdminOnly()` |
| `GET /reference/imports` | `backend/src/domain/reference/controller/reference.controller.ts` | `@AdminOnly()` |

`@AdminOnly()`(= `@Auth()` + `IS_ADMIN` 메타)는 전역 JWT 가드 **뒤에** 실행되는 역할 가드를 추가할 뿐이다. 토큰이 유효했다면 결과는 **200 또는 403**이지 401일 수 없다. → **설정/참조 로직 자체의 결함이 아님.**

### 2.3 프론트 토큰 수신·첨부 (현재는 존재함 — 선행 REQ로 구현 완료)

| 항목 | 파일 | 동작 |
|------|------|------|
| SSO 부트스트랩 | `frontend/src/lib/ama-token.ts` (`bootstrapAmaAuth`) | 부팅 1회 `?ama_token` 우선 → 없으면 `localStorage['hsc_token']`. 디코드 후 **만료 아니면** `setAuth`, 만료/파싱불가면 `clear()` |
| 스토어 초기값 | `frontend/src/stores/auth.store.ts:20-22` | `token = localStorage.getItem('hsc_token')`, `user = null` |
| Bearer 첨부 | `frontend/src/lib/api-client.ts:17-23` | 인터셉터가 `store.token` 존재 시 `Authorization: Bearer {token}` 첨부 |
| 설정 서비스 | `frontend/src/services/admin-settings.service.ts` | `GET /admin/settings/${category}` |
| 참조 서비스 | `frontend/src/services/reference.service.ts` | `GET /reference/imports` |
| 디버그 패널 | `frontend/src/components/common/DebugContextPanel.tsx` | AMA 유저(name/email/roles/entityId/entityCode/scope/**exp**/원본 JWT/디코드 payload) 표기 |

**증거 체인**:
1. 디버그 패널에 유저가 뜬다 → 부트스트랩이 토큰을 디코드하고 `setAuth` 호출 성공(= 로드 시점 **만료 아님**) →
2. 스토어에 token 존재 → 인터셉터가 **Bearer 첨부** →
3. 그럼에도 백엔드 401 → **서명 검증 실패** (선행 REQ의 "토큰 미첨부" 원인과 명백히 다름)

### 2.4 스테이징 실측 (SSH 확인)

| 항목 | 값 | 확인 방법 |
|------|-----|-----------|
| 스테이징 hscode BFF `JWT_SECRET` | `amb_jwt_staging_secret_key_32bytes!` | `docker exec bff-app-hscode printenv` |
| 스테이징 AMA API(`amb-api-staging`) `JWT_SECRET` | `amb_jwt_staging_secret_key_32bytes!` | `docker exec amb-api-staging printenv` |
| 정합성 | **일치** | — |
| 정상 서명 토큰(스테이징 시크릿, `scope:'app_store:context'`, `role:'ADMIN'`)으로 직접 호출 | **401 아님** — 컨트롤러까지 도달 | 컨테이너 내부 `jsonwebtoken` 서명 후 `curl localhost:3102` |

> **결론**: 스테이징 BFF는 **스테이징 AMA가 서명한 토큰을 정상 인증**한다. 즉 브라우저의 401은 "스테이징 AMA가 서명하지 않은 토큰"임을 강하게 시사한다.

### 2.5 토큰 발급 측(AMA) 현황

| 항목 | 파일(ambManagement) | 내용 |
|------|--------------------|------|
| App Store SSO 토큰 발급 | `apps/api/src/domain/entity-settings/service/app-store.service.ts` → `generateAppStoreToken()` | `scope:'app_store:context'`, `extra:{appSlug}` |
| 서명 방식 | `apps/api/src/global/service/iframe-token.service.ts` → `sign()` | **`signingSecret` 미지정 → 전역 `JWT_SECRET`으로 HS256 서명, 기본 만료 `1h`** |
| 대조군(커스텀 앱/카테고리) | `entity-custom-app.service.ts` 등 | **앱별 `ecaJwtSecretEnc`** 사용 (앱스토어 경로엔 앱별 시크릿 없음) |

→ App Store 경로는 **AMA 전역 `JWT_SECRET`에 100% 의존**한다. 따라서 **"어느 환경의 AMA가 토큰을 발급했는가"** 가 인증 성패를 좌우한다. (프로덕션 `ama.amoeba.site`에서 스테이징 앱으로 진입 시 → prod 전역 시크릿 서명 토큰이 스테이징 BFF에 도달 → 서명 불일치 → 401.)

### 2.6 부수 발견 — `ent_id` uuid 캐스트 취약점 (별개 잠재 결함)

- `hsm_app_settings.ent_id`, `hsm_import_batches.ent_id`는 Postgres **`uuid`** 타입(`sql/hscode-manager-schema.sql`, `backend/.../entity/app-setting.entity.ts`).
- 테스트에서 **비-UUID `entityId`("ent-test-1")** 를 담은 정상 서명 토큰으로 호출 시 두 엔드포인트가 **500(HSC-E9999)** 발생 → Postgres `invalid input syntax for type uuid`로 추정.
- 실제 AMA 토큰의 `entityId`는 UUID이므로 프로덕션 증상(401)과는 무관하나, **입력 방어 부재**는 견고성 결함으로 문서화한다.
- 스키마 자체는 정상: `hsm_app_settings` 포함 10개 테이블 모두 `sql/hscode-manager-schema.sql`에 정의됨(테이블 누락 아님).

### 2.7 AS-IS 문제점 요약

| # | 문제 | 근거 |
|---|------|------|
| P1 | 설정 화면의 두 API가 401 → 관리자 설정/참조 기능 전면 사용 불가 | 사용자 콘솔 |
| P2 | 401 원인이 코드가 아닌 **토큰 서명 주체(AMA 환경) 불일치 또는 만료**에 있음 | §2.1·§2.4·§2.5 |
| P3 | 세션 중 토큰 만료 시 재인증 유도 없음 → 무한 401 | `bootstrapAmaAuth`는 부팅 1회만 만료 검사 |
| P4 | `ent_id` 비-UUID 입력에 대한 방어 부재 → 500 | §2.6 |
| P5 | 라이브 토큰의 `exp`/서명 주체를 즉시 판별하는 표준 진단 절차 미확립 | 디버그 패널은 있으나 운용 규약 없음 |

## 6. 기술 제약사항

- **환경 격리**: App Store SSO 토큰은 발급 AMA의 **전역 `JWT_SECRET`** 에 의존(앱별 시크릿 없음). 스테이징 앱은 반드시 **스테이징 AMA**에서 진입해야 하며, `JWT_SECRET`은 환경쌍(stg↔stg, prod↔prod)으로 일치해야 한다.
- **토큰 수명**: App Store 토큰 기본 만료 `1h`(`IframeTokenService`). 장시간 세션에서 만료 필연 → 재인증 처리 필수.
- **보안(POL-005)**: 설정 비밀값(`aps_is_secret`)은 암호화 저장·마스킹 노출 유지. 디버그 패널은 원본 JWT를 노출하므로 **운영 환경 상시 노출 여부 재검토**(진단 용도 한정 권장).
- **멀티테넌시**: `ent_id`는 UUID(CHAR/UUID) 전제. 비-UUID 유입 시 캐스트 오류(500) 방지를 위한 검증 필요.
- **호환성**: 정상 동작 중인 car-manager 등 타 앱의 SSO 패턴과 처방 방향을 일관화.
