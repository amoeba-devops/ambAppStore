- 대상: HS Code Manager `/app-hscode` — 문서 업로드 매칭(Phase 2)
- 선행: 통관 AI 에이전트 Phase 2(matching) 라이브

## 1. 요구사항 요약
| # | 요구사항 | 유형 |
|---|----------|------|
| R1 | 대량 업로드(수백~수천 품목) 처리 — 100행 상한·타임아웃 제거 | 필수 |
| R2 | 업로드 즉시 접수 응답(요청건 PROCESSING) 후 백그라운드 매칭 | 필수 |
| R3 | 진행률 제공(처리 n/총 m) — 결과 화면 폴링 표시 | 필수 |
| R4 | 개별 품목 실패 격리·내결함성(전체 중단 없음) | 필수 |
| R5 | 2코어·CPU TEI 보호(워커 동시성 상한·예산 가드) | 필수 |
| R6 | 기존 동기 결과·승인/저장 흐름과 호환(결과·confirm 무변경) | 필수 |

## 2. AS-IS 현황
- `MatchingService.uploadAndMatch`가 **동기** — 파싱 후 품목을 for 루프로 순차 매칭하고 **한 HTTP 요청 안에서** 완료까지 대기.
- `DocumentParserService` `MAX_ITEMS=100` — 초과분 잘라내고 parseNote에 명시.
- 문제: 대량 파일 → 요청 타임아웃/잘림, 진행률 없음(블로킹), 2코어+CPU TEI에서 특히 느림.
- 자산: **BullMQ 인프라 존재**(redis-hscode + bullmq, 레거시 `excel` 도메인이 registerQueue/WorkerHost/job.updateProgress로 이미 사용). Redis 연결은 app.module `BullModule.forRootAsync` 전역 설정.

## 3. TO-BE
```
POST /matching/upload
  → 파싱 → 요청건 생성(status=PROCESSING) → 품목(items) 생성(추천 없음)
  → BullMQ 큐에 job{mrqId} 투입 → 즉시 요청건 요약 응답(mrqId, itemCount, PROCESSING)
[워커] MatchingProcessor
  → 요청건의 미처리 품목마다 matchItem(면장+기준표 RAG → AI 재판정 → 추천 저장)
  → 품목마다 processed_count++ (진행률)
  → 완료 시 matched/review 집계 + status=READY
GET /matching/requests/:id → 현재 상태(processed/itemCount, status)
[프론트] 결과 화면이 PROCESSING 동안 폴링 → 진행바 → READY 시 결과 표시
```
- 승인/저장(confirm)·요청건 이력은 **무변경**(READY 이후 동일).
- 상한: MAX_ITEMS를 대폭 상향(예: 2000) — 비동기가 처리.

## 4. 갭 분석
| 영역 | 현재 | 변경 | 영향 |

## 6. 기술 제약
- 워커 concurrency 낮게(2~4) — 2코어+CPU TEI 보호(R5). Claude 일일 예산 가드 유지.
- 개별 품목 try/catch 격리(R4) — 실패 품목은 검토필요로 남기고 계속.
- 유효 키 미설정 시 AI 폴백 그대로(무중단).
- 범위 외(후속): PDF 파싱(다음 작업), 취소/재시도 UI.
