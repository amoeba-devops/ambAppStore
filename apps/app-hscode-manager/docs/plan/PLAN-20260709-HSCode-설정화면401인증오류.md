# 작업계획서 — HS Code Manager 설정(admin) 화면 401 인증 오류

- **문서 ID**: PLAN-20260709-HSCode-설정화면401인증오류
- **작성일**: 2026-07-09
- **대상 앱**: HS Code Manager (`/app-hscode`)
- **선행 문서**: [`REQ-20260709-HSCode-설정화면401인증오류`](../analysis/REQ-20260709-HSCode-설정화면401인증오류.md)
- **브랜치**: `feature/hscode-manager`
- **핵심 성격**: 401은 코드 결함이 아니라 **토큰 서명 주체(AMA 발급 경로) vs BFF 검증 시크릿 불일치** 또는 **만료**가 유력. 따라서 **Phase 0(근본원인 확정)을 결정 게이트**로 두고, 확정 결과에 따라 처방 분기(1A/1B)한다.

---

## 1. 시스템 개발 현황 분석

### 1.1 디렉토리 구조 (복구 완료)
```
apps/app-hscode-manager/            # feature/hscode-manager 브랜치에서 추적(64ea39e 최초 커밋)
├── backend/  (NestJS, 98 TS, 11 도메인: admin-settings, reference, excel, gtin, ...)
│   └── src/auth/  guards(jwt-auth·entity-scope·role) · jwt.strategy · decorators(auth·admin-only·public)
├── frontend/ (React18+Vite, 6 페이지, lib/ama-token.ts · lib/api-client.ts · stores/auth.store.ts)
├── sql/hscode-manager-schema.sql   (10 테이블, hsm_app_settings 포함)
└── docs/ (analysis/REQ · plan · test · design)
```

### 1.2 기술 스택
- FE: React 18 + TS + Vite, Zustand(auth), React Query 5, react-i18next(ko/en/vi), axios
- BE: NestJS 10 + TypeORM + **PostgreSQL 15(pgvector)** + Redis(BullMQ)
- 인증: 전역 `JwtAuthGuard`(passport-jwt, `APP_GUARD`) + `@Auth()`/`@AdminOnly()` (ent_id 격리 + 역할)

### 1.3 기존 코드 상황 (검증된 현황)

| 항목 | 파일 | 현재 상태 |
|------|------|-----------|
| 전역 JWT 검증 | `backend/src/auth/jwt.strategy.ts` | `secretOrKey: process.env.JWT_SECRET`, `ignoreExpiration:false` → 미첨부/서명불일치/만료 시 **401** |
| 토큰 캡처 | `frontend/src/lib/ama-token.ts` `bootstrapAmaAuth()` | 부팅 1회 `?ama_token`→localStorage, 디코드·만료검사 후 `setAuth`. **선행 REQ(20260708)로 구현 완료** |
| Bearer 첨부 | `frontend/src/lib/api-client.ts` | 요청 인터셉터만 존재. **응답(401) 인터셉터 없음** |
| 게이팅/재인증 UI | `frontend/src/router.tsx`, `components/common/` | **없음** (인증 가드 래퍼·재인증 안내 컴포넌트 부재. `DebugContextPanel`만 존재) |
| 디버그 패널 | `frontend/src/components/common/DebugContextPanel.tsx` | 라이브 토큰 `scope`/`exp`/원본 JWT/디코드 payload 노출 (← Phase 0 진단 도구) |

### 1.4 AMA 토큰 발급 경로 (근본원인 규명 핵심)

| 경로 | 발급 코드(ambManagement) | 서명 시크릿 | hscode BFF(전역 secret) 검증 결과 |
|------|--------------------------|-------------|----------------------------------|
| **app_store** | `app-store.service.ts` `generateAppStoreToken()` — `scope:'app_store:context'`, `signingSecret` 미지정 | **전역 `JWT_SECRET`** | ✅ 통과 (staging BFF secret == AMA 전역 secret, 환경무관 단일 발급 확정) |
| **custom_app** | `entity-custom-app.service.ts:183` — `ecaJwtSecretEnc` 있으면 앱별, NULL이면 전역 fallback (`20260610-eca-jwt-secret.sql`) | **앱별 `ecaJwtSecretEnc`**(설정 시) | ✗ **401** (앱별 서명 ↔ 전역 검증 불일치 = car-v2 "Invalid token" 동형) |

> hscode가 어느 경로로 진입하는지는 **AMA 런타임 DB 상태**(EntityCustomApp 등록/`ecaJwtSecretEnc` 유무)이며 정적 판별 불가 → **라이브 토큰 `scope`로 확정**한다.

### 1.5 제약사항
- 스테이징/프로덕션 TypeORM `synchronize` 비활성 → 스키마 변경 시 수동 SQL. (본 건은 스키마 변경 없음)
- App Store SSO 토큰 기본 만료 `1h`(`IframeTokenService`).
- `VITE_*`는 빌드 시점 인라인 → 프론트 변경 시 이미지 재빌드 필수(`deploy-staging.sh`).
- 배포는 스테이징 먼저(`deploy-staging.sh`), 직접 `docker compose build` 금지.
- 커밋은 `git add apps/app-hscode-manager`로 범위 한정.

## 2. 단계별 구현 계획

### Phase 0 — 근본원인 확정 (결정 게이트, 코드변경 0)

- **Step 0-1**: 브라우저에서 `stg-apps.amoeba.site/app-hscode/admin` 진입 → **DebugContextPanel**에서 라이브 토큰의 `scope`·`exp`·원본 JWT 확보.
  - `scope == 'app_store:context'` → **경로=app_store(전역 secret)** → 401 원인은 **만료** 또는 (예외적)시크릿 불일치 → **Phase 1B**
  - `scope == 'custom_app:context'`(또는 app별) → **경로=custom_app(앱별 secret)** → 401 원인은 **서명 불일치** → **Phase 1A**
  - └─ 사이드 임팩트: 없음(읽기 전용 진단).
- **Step 0-2**: 원본 JWT를 스테이징 BFF `JWT_SECRET`으로 검증 시도(참: app_store / 거짓: custom_app 확증). `exp` 시각으로 만료 여부 병행 확인.
  - └─ 사이드 임팩트: 없음(로컬 검증). AMA/BFF 무변경.
- **Step 0-3**: AMA에 등록된 `/app-hscode` 앱의 **URL이 가리키는 환경(stg/prod)**과 **EntityCustomApp.`ecaJwtSecretEnc` 유무** 확인(AMA 운영자/DB).
  - └─ 사이드 임팩트: 없음(조회). **이 게이트 통과 후에만 Phase 1 처방 확정.**

### Phase 1A — [custom_app 경로일 때] 서명·검증 시크릿 정합 (택1)

- **Step 1A-옵션①(권장·최소변경)**: AMA에서 hscode EntityCustomApp의 `ecaJwtSecretEnc`를 **NULL로 정렬 → 전역 `JWT_SECRET` fallback** 사용. 이후 발급 토큰이 hscode BFF(전역 secret)와 일치.
  - └─ 사이드 임팩트: 해당 앱 기존 발급 토큰(앱별 서명분) 무효화 → 사용자 **재진입 1회 필요**. 타 앱 무영향.
- **Step 1A-옵션②**: hscode BFF가 **앱별 secret**을 검증하도록 `JWT_SECRET`을 해당 `ecaJwtSecretEnc` 평문값으로 설정(`bff-app-hscode` `.env`).
  - └─ 사이드 임팩트: BFF 재기동 필요. 시크릿 회전 시 재설정 부담 → 옵션①이 운영상 유리.
- **결정 기준**: car-v2 처방과 일관되게 선택(car-v2가 옵션①/전역공유로 수렴했으면 동일 적용).

### Phase 1B — [app_store 경로 & 만료가 원인일 때] 프론트 401 재인증

- **Step 1B-1**: `api-client.ts`에 **응답 인터셉터** 추가 — 401 수신 시 `useAuthStore.clear()` + 재인증 안내 상태 트리거.
  - └─ 사이드 임팩트: 전 API 공통 경로 변경 → 정상 401(권한없음 아님)만 처리하도록 분기, 무한 리다이렉트 방지 가드 필요.

### Phase 2 — 만료/무토큰 공통 처리 & 안내 UI (경로 무관 공통)

- **Step 2-1**: 인증 게이트 도입 — 토큰 없음/만료 시 본문 대신 **재인증 안내**(AMA 재진입 유도) 렌더. 라우터 상위 또는 `App` 레이아웃에 배치.
  - └─ 사이드 임팩트: 최초 렌더 흐름 변경 → 정상 토큰 경로 회귀 테스트 필요.
- **Step 2-2**: i18n 문구 추가(`locales/{ko,en,vi}`) — "세션이 만료되었습니다 / 다시 로그인" 등. 새 네임스페이스 시 `i18n.ts` 등록.
  - └─ 사이드 임팩트: 3개 언어 누락 시 키 노출 → 3언어 동시 작성.

### Phase 3 — 백엔드 견고성: ent_id UUID 방어 (별개 잠재결함)

- **Step 3-1**: `entityId`가 UUID 형식이 아닐 때 Postgres `uuid` 캐스트 500 대신 명확한 4xx 반환. `EntityScopeGuard` 보강 또는 전용 `ParseUuidPipe`/검증 유틸 적용.
  - └─ 사이드 임팩트: 정상 UUID 토큰은 무영향. 프로덕션 401 증상과 무관하나 방어적 안정화.

### Phase 4 — 검증 & 배포

- **Step 4-1**: 로컬/스테이징에서 정상 토큰 진입 → 설정/참조 200 확인, 만료 시 재인증 안내 확인.
  - └─ 사이드 임팩트: 없음.
- **Step 4-2**: `deploy-staging.sh`로 스테이징 배포(프론트 변경 시 재빌드) → 실사용 진입 검증 → 이후 `main`/`production` 절차.
  - └─ 사이드 임팩트: 프론트 재빌드 시 `VITE_*` 인라인 갱신. 스테이징 우선 원칙 준수.

## 4. 사이드 임팩트 분석

| 범위 | 위험도 | 설명 |
|------|--------|------|
| AMA 앱 토큰(1A 옵션①) | 중 | `ecaJwtSecretEnc` NULL화 시 기존 발급 토큰 무효 → **재진입 1회** 필요. 타 앱 무영향(앱별 격리) |
| BFF `.env` `JWT_SECRET`(1A 옵션②) | 중 | 변경 시 **모든** hscode 세션 재인증. 시크릿 회전 시 재설정 필요 → 옵션① 대비 운영 부담↑ |
| api-client 응답 인터셉터 | 중 | 전 API 공통 경로. 401(인증)만 처리하고 정상 데이터 흐름/403(권한)과 분리, 무한 리다이렉트 방지 필수 |
| 인증 게이트 | 중 | 최초 렌더 게이팅 → 정상 토큰 경로 회귀 필요(모든 페이지 진입 영향) |
| i18n 3언어 | 낮음 | 누락 시 키 노출. ko/en/vi 동시 작성으로 회피 |
| ent_id UUID 방어 | 낮음 | 정상 UUID 무영향. 방어 로직 추가만 |
| 배포(프론트 재빌드) | 낮음 | `VITE_*` 인라인 → 이미지 재빌드 필수, `deploy-staging.sh` 경유 |

## 5. DB 마이그레이션

- **불필요**. `hsm_app_settings` 등 전 테이블이 `sql/hscode-manager-schema.sql`에 정의·적용 완료. 본 건은 인증(토큰 서명/검증) 정합 + 프론트 예외처리 + 백엔드 입력검증으로, **스키마 변경 없음**.
- (참고) `ent_id`는 `uuid` 타입 유지. Phase 3는 애플리케이션 레벨 검증이며 DDL 변경 아님.
