# 작업계획서 — 문서 업로드 매칭 대량 비동기 (BullMQ)

- 문서 ID: PLAN-20260710-대량비동기매칭
- 선행: REQ-20260710-대량비동기매칭
- 재사용: BullMQ(redis-hscode, app.module BullModule.forRootAsync), excel 도메인 패턴(registerQueue/WorkerHost/updateProgress), MatchingService.matchOne 로직

## 1. 시스템 현황
- matching 도메인: MatchRequest·Item·Recommendation 엔티티, MatchingService(uploadAndMatch 동기), DocumentParserService, MatchingController.
- BullMQ 전역 연결 존재. 신규 큐만 registerQueue.

## 2. 단계별 구현

### Phase 1 — 스키마
- **Step 1-1**: 마이그레이션 `20260710-matching-async.sql` — `hsm_match_requests`에 `mrq_processed_count INTEGER DEFAULT 0` 추가.
  - └─ 사이드 임팩트: 컬럼 1개, 기존 무변경.

### Phase 2 — 백엔드 비동기 파이프라인
- **Step 2-1**: `matching.constants.ts` — `MATCHING_QUEUE='matching-process'`.
- **Step 2-2**: MatchingService 리팩터
  - `uploadAndMatch` → **enqueue 방식**: 파싱 → 요청건(PROCESSING) → 품목 생성(createItem, 추천 없음) → `queue.add('process',{mrqId})` → 요청 요약 반환.
  - `matchItem(item)` 신규: 기존 matchOne의 매칭부(면장+지식 회수→AI→추천 저장→needsReview)만 분리, 입력은 저장된 Item(productNameKo/mainMaterial/intendedUse).
  - `processRequest(mrqId)` 신규(워커 호출): 미처리 품목 순회→matchItem→processed_count++→완료 시 matched/review 집계+status READY.
  - └─ 사이드 임팩트: 업로드 응답이 요약(items는 생성됐으나 추천 없음). 프론트 폴링 필요.
- **Step 2-3**: `MatchingProcessor`(WorkerHost, @Processor(MATCHING_QUEUE)) — process(job)→matchingService.processRequest(mrqId). 동시성은 워커 옵션(concurrency 3).
  - └─ 사이드 임팩트: 2코어 보호 위해 concurrency 낮게.
- **Step 2-4**: matching.module — BullModule.registerQueue({name:MATCHING_QUEUE}) + MatchingProcessor provider.
- **Step 2-5**: DocumentParserService MAX_ITEMS 100→2000.

### Phase 3 — 프론트
- **Step 3-1**: useMatchRequest에 refetchInterval(status===PROCESSING 동안 폴링).
- **Step 3-2**: MatchResultPage — PROCESSING 시 진행바(processed/itemCount)+"분석 중" 표시, READY 시 결과.
- **Step 3-3**: i18n(진행중/분석중 키).

### Phase 4 — 검증·배포
- 스테이징 먼저: 대량(수백행) 업로드→즉시 응답→폴링 진행률→READY→승인. 소량 회귀. → 프로덕션.
