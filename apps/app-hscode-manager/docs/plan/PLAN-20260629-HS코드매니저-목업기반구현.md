# HS Code Manager — 작업계획서 (목업 기반 실제 구현)

> 요구사항분석서 `REQ-20260629-HS코드매니저-목업기반구현.md`를 구현 단계로 분해한다. 각 Step에 사이드 임팩트를 명시한다. 범위는 **MVP(Feature A + C + 참조 Import + 결과 상세)** 우선이며, Feature B 외부 레이어는 후속 Phase로 분리한다.

## 1. 시스템 개발 현황 분석

### 1.1 디렉토리 구조 (TO-BE 목표)
```
apps/app-hscode-manager/
├── backend/                      # NestJS BFF (포트 3102)
│   ├── src/
│   │   ├── main.ts / app.module.ts
│   │   ├── auth/                 # AMA JWT SSO + ent_id guard
│   │   ├── common/               # 표준응답·예외필터·DTO·util
│   │   └── domain/
│   │       ├── search-core/      # FN-001~003 공통 엔진
│   │       ├── search-qa/        # SCR-001 / FR-001~007
│   │       ├── gtin/             # SCR-002 / FR-010~022
│   │       ├── attribute/        # SCR-003 폼 / FR-030/033
│   │       ├── excel/            # SCR-003 엑셀 / FR-031~036
│   │       ├── reference/        # SCR-005 참조: RAG 코퍼스 import / FR-040/044/002
│   │       ├── review/           # SCR-005 참조: 검토 / FR-019/018
│   │       ├── mapping/          # SCR-005 참조: 매핑편집 / FR-043
│   │       ├── result/           # SCR-004 공통결과
│   │       ├── audit/            # FR-020 감사
│   │       └── admin-settings/   # SCR-006 어드민(설정): AI/API 연결·설정 / R-18
│   ├── Dockerfile
│   └── .env (PostgreSQL 블록)
├── frontend/                     # React + Vite SPA (포트 5202, base /app-hscode)
│   ├── src/{pages,components,hooks,services,stores,i18n,lib}
│   └── Dockerfile
├── sql/hscode-manager-schema.sql # + pgvector 보강
└── docker-compose.hscode.yml
```

### 1.2 기술 스택 (확정)
- **Frontend**: React 18 + TS 5 + Vite 5 + TailwindCSS 3, Zustand + React Query 5 + React Hook Form + Zod, React Router, SSE(명확화 스트리밍), lucide-react, i18next(ko/en/vi)
- **Backend**: NestJS 10 + TypeORM 0.3 + **PostgreSQL 15 (pgvector)** + Redis(BullMQ), `@nestjs/swagger`
- **AI/외부**: Claude `claude-sonnet-4-6`(명확화 질문·L4 분류) + 다국어 임베딩(**[TBD] Phase 0**) + VN-bieu-thue/KR-customs 어댑터(기존 토글)
- **인프라**: Docker compose(BFF 3102/FE 5202/PostgreSQL/Redis) + Nginx `/app-hscode/*`

### 1.3 기존 코드 상황
- `backend/src`·`frontend/src` **부재** → 전면 신규.
- `backend/dist`는 **별개 설계 계보**(item/classification/inquiry/verification/master-* 등) → 재사용 불가, `auth`/`common` **패턴만** 참고.
- 설계문서 8종·DDL·목업(i18n 사전 포함)은 **재사용 자산**.

### 1.4 제약사항 (분석서 §6 승계)
DB 이원화(C-1), 임베딩 공급자 TBD(C-2, MVP 선행), 교차언어(C-3), 외부 API 미프로비저닝(C-4), 대용량 비동기(C-6), 성능 NFR(C-7), 멀티테넌시(C-9), 법적고지(C-10).

## 2. 단계별 구현 계획

### Phase 0 — 기반/인프라 셋업 (선행)
- **Step 0.1** 모노레포 스캐폴드: `backend`(Nest CLI)·`frontend`(Vite) package.json/tsconfig/lint, 루트 workspaces·turbo 등록
  └─ 사이드 임팩트: 루트 `package.json`/`turbo.json` 변경 → 다른 앱 빌드 파이프라인 영향 없도록 scope 한정
- **Step 0.2** PostgreSQL 15 + pgvector 컨테이너 구성, `.env` DB 블록 MySQL→PostgreSQL 교체
  └─ 사이드 임팩트: 플랫폼 표준 MySQL과 이원화 → 배포/Nginx/compose에 별도 DB 명시, 운영 문서화 필요
- **Step 0.3** **임베딩 공급자 PoC/선정**(multilingual-e5/Cohere/OpenAI) → 차원 N 확정
  └─ 사이드 임팩트: pgvector 컬럼/인덱스 DDL·검색 정확도(NFR-003) 전반에 영향 → **Phase 1 진입 차단 의존성**
- **Step 0.4** auth/common 작성: AMA JWT SSO 검증, `@Auth()`/`@Public()`/`@Roles()`, entity-scope guard, 표준응답·전역예외필터(`HSC-Exxxx` 에러코드)
  └─ 사이드 임팩트: 전 도메인 컨트롤러가 의존 → 인터페이스 안정화 우선

### Phase 1 — DB 스키마 & 참조(Reference) Import = RAG 코퍼스 구축 (Feature 공통 base, FR-040/044/002)
> 참조 데이터는 Feature A/C 분류의 **RAG 지식 소스**다. import→중복제거→임베딩→pgvector 적재가 곧 검색 품질의 기반.
- **Step 1.1** 9개 TypeORM 엔티티 작성(hsm_*) + nullable 컬럼 명시적 type 지정(CLAUDE.md MUST)
  └─ 사이드 임팩트: 모든 도메인 서비스의 기반 → 컬럼/관계 변경 시 광범위 영향
- **Step 1.2** DDL 보강(pgvector extension + `hsr_embedding vector(N)` + HNSW 인덱스), 수동 마이그레이션 SQL 정리(§5)
  └─ 사이드 임팩트: 대용량 `hsm_hs_references` 인덱스 빌드 시간 → 배포 윈도우 고려
- **Step 1.3** Import 어댑터 3종(BaoCaoHangChiTiet/ToKhai/VMSG) + 디스패처(FN-040) + 중복제거(FN-041, HS+품명+원산지+단위)
  └─ 사이드 임팩트: VMSG/ToKhai 컬럼 매핑 [TBD] → 미지원 형식은 "어댑터 필요" 상태로 graceful 처리
- **Step 1.4** 임베딩 생성 파이프라인(신규 행 → 임베딩 → pgvector upsert)
  └─ 사이드 임팩트: 임베딩 호출량/비용 → 배치·레이트리밋(POL-004)
- **Step 1.5** 코퍼스 시드 적재(~94.7k행) + 전역 ref 시드(gpc/country-ext)
  └─ 사이드 임팩트: 초기 적재 부하 → 비동기 배치

### Phase 2 — Feature A (Q&A) + 공통 검색 코어 (SCR-001/004, FR-001~007)
- **Step 2.1** search-core: semantic-retrieval(FN-001, pgvector ANN + 키워드 폴백), result-assembler(FN-003, FR-041 정규화 결과)
  └─ 사이드 임팩트: Feature C가 동일 엔진 재사용 → 인터페이스 공용 설계 필수
- **Step 2.2** clarifying-question(FN-002, Claude): gap<0.08 시 1질문, 최대 5라운드(POL-001)
  └─ 사이드 임팩트: Claude 호출 비용(`AI_DAILY_BUDGET_USD`) → 예산 가드/캐시
- **Step 2.3** qa.controller(SSE 스트리밍) + `POST /qa/search`·`POST /qa/confirm`(hsm_query_logs + audit)
  └─ 사이드 임팩트: SSE는 Nginx 버퍼링/타임아웃 설정 영향 → 프록시 설정 동반
- **Step 2.4** 프론트 SCR-001(채팅 transcript·CandidateCard·ClarifyChips·ConfirmButton) + SCR-004(결과 상세: 근거출처·해석메타·신뢰도밴드·법적고지)
  └─ 사이드 임팩트: SCR-004는 3모드 공통 → 결과 객체 스키마 고정 후 구현
- **Step 2.5** audit 모듈(FN-018, append-only) + 법적고지 컴포넌트(FR-022)
  └─ 사이드 임팩트: 전 모드가 audit 기록 → 공통 서비스화

### Phase 3 — Feature C (속성/엑셀) (SCR-003, FR-030~036)
- **Step 3.1** attribute: 폼 핸들러(FN-030) → search-core 라우팅 + `POST /attributes/classify`
  └─ 사이드 임팩트: Feature A 엔진 재사용 → Phase 2 완료 의존
- **Step 3.2** excel-validator(FN-031): 컬럼/타입/필수 검증 + 행별 오류 리포트(FR-032), 템플릿 다운로드(FR-035)
  └─ 사이드 임팩트: 템플릿 스키마 = 코퍼스 컬럼과 정합 필요
- **Step 3.3** batch-classifier(FN-032, BullMQ worker): 유효행 큐 적재·행별 분류·저신뢰 플래그(FR-036) + 진행률(`GET jobs/:id`)
  └─ 사이드 임팩트: Redis 인프라 의존 + 워커 동시성 → DB 커넥션 풀 영향
- **Step 3.4** excel-export(FR-034): 입력행 + HS/신뢰도/근거 컬럼 추가 워크북 생성
- **Step 3.5** 프론트 SCR-003(속성 폼 + Dropzone + ValidationReport + ResultsTable + 진행률바 + 다운로드)
  └─ 사이드 임팩트: 대용량 업로드 → 멀티파트 한도/타임아웃 Nginx 설정

### Phase 4 — Feature B 바코드 (SCR-002, MVP=L1+확장 / 외부=후속)
- **Step 4.1** gtin-normalizer(FN-010, 14자리) + 체크디지트 검증(FN-011) + `POST /gtin/resolve`
  └─ 사이드 임팩트: invalid는 조회 전 차단 → 외부 호출 비용 0
- **Step 4.2** layer1-direct-map(FN-011) + country-expander(FN-015, HS6→8~10자리+관세) + 법적고지
  └─ 사이드 임팩트: country-ext 미존재 시 HS6만 반환 + 플래그
- **Step 4.3** 프론트 SCR-002(GTIN/도착국 입력 + 해석결과 패널 + PipelineLayers + 학습/검토 안내)
  └─ 사이드 임팩트: PipelineLayers는 후속 L2~L4 상태 표시 → 단계 enum 확장 가능 설계
- **Step 4.4 [후속]** L2 제품정보(GS1, FN-012 stub→실연동) / L4 Claude AI 분류(FN-014) / 학습 자동저장(FN-016) / 검토 큐 라우팅(FN-017)
  └─ 사이드 임팩트: 외부 API 프로비저닝(C-4) 의존 → MVP 분리

### Phase 5 — 참조(Reference) 화면 + 어드민(설정) (SCR-005/006)

**5A. 참조(Reference) — SCR-005, `/app-hscode/reference` (FR-040/044/018/019/043)**
- **Step 5.1** 참조 import UI(RAG 코퍼스 적재): Dropzone + 배치 요약 테이블 + 형식 자동감지 노출 (Phase 1 백엔드 연결)
  └─ 사이드 임팩트: 적재 결과가 Feature A/C 검색 컨텍스트 품질을 직접 변화 → 임베딩 재생성 트리거
- **Step 5.2** review 모듈: 검토 큐 조회 + 승인/할당 → 승인 시 learned 저장(source=manual, FN-016)
  └─ 사이드 임팩트: 승인이 hsm_gtin_hs_maps에 write → L1 적중률 변화
- **Step 5.3** mapping 편집: GTIN/GPC/country-ext CRUD + 국가확장 미리보기(FR-043)
  └─ 사이드 임팩트: 전역 ref 수정 → 전 테넌트 검색결과 영향, 역할 제한 필수(POL-005)

**5B. 어드민(설정) — SCR-006(신규), `/app-hscode/admin` (R-18, NFR-007/POL-001/POL-004)**
- **Step 5.4** `hsm_app_settings` 엔티티 + app-config.service(카테고리: AI/EXTERNAL/EMBEDDING/THRESHOLD/CACHE) + 비밀값 암호화 저장
  └─ 사이드 임팩트: .env 정적값 → DB 동적 오버라이드. 런타임 설정 캐시 무효화 전략 필요
- **Step 5.5** admin-settings.controller(역할 제한) + 설정 변경 audit 기록 + 연결 테스트(예: Claude/어댑터 ping)
  └─ 사이드 임팩트: 잘못된 설정이 분류 전체 중단 유발 → 검증·기본값 폴백, 비밀값 평문 노출 금지
- **Step 5.6** 프론트 SCR-006 설정 화면(카테고리 탭 + 마스킹된 키 입력 + 임계치 슬라이더 + 어댑터 토글)
  └─ 사이드 임팩트: 목업 미포함 화면 → 목업 후속 갱신(nav `관리자`→`참조`, `설정` 탭 신규)

### Phase 6 — i18n / 배포 / 검증
- **Step 6.1** i18n: 목업 ko/en/vi 사전 → `locales/{ko,en,vi}/hscode.json` 이식 + 네임스페이스 등록
- **Step 6.2** Docker/Nginx/compose: BFF 3102·FE 5202·`/app-hscode/*` 라우팅·SSE 프록시·업로드 한도
  └─ 사이드 임팩트: 기존 플랫폼 Nginx conf 수정 → 타 앱 라우팅 회귀 점검
- **Step 6.3** 스테이징 배포(`deploy-staging.sh` 경유) + 검증, 성능(NFR-001/002)·정확도(NFR-003) 측정
  └─ 사이드 임팩트: PostgreSQL 컨테이너 추가 → 스테이징 리소스 영향

## 5. DB 마이그레이션

> 스테이징/프로덕션 TypeORM `synchronize=false` (CLAUDE.md MUST). 아래 **수동 SQL**을 순서대로 적용.

```sql
-- ① 확장 + DB
CREATE EXTENSION IF NOT EXISTS vector;

-- ② 9개 테이블 DDL — sql/hscode-manager-schema.sql 그대로 적용
--    (hsm_gtin_hs_maps, hsm_gpc_hs_maps, hsm_hs_country_extensions,
--     hsm_product_masters, hsm_import_batches, hsm_hs_references,
--     hsm_query_logs, hsm_review_queues, hsm_resolution_audits)

-- ③ pgvector 보강 (차원 N은 Phase 0 임베딩 공급자 확정 후 치환)
ALTER TABLE hsm_hs_references ADD COLUMN hsr_embedding vector(N);
CREATE INDEX idx_hsm_hs_references_embedding
  ON hsm_hs_references USING hnsw (hsr_embedding vector_cosine_ops);

-- ③-b 어드민(설정) 테이블 (SCR-006, R-18)
CREATE TABLE hsm_app_settings (
  aps_id         UUID         NOT NULL DEFAULT gen_random_uuid(),
  ent_id         UUID         NOT NULL,
  aps_category   VARCHAR(16)  NOT NULL,        -- AI | EXTERNAL | EMBEDDING | THRESHOLD | CACHE
  aps_key        VARCHAR(64)  NOT NULL,
  aps_value      TEXT         NULL,            -- 비밀값은 암호화 저장
  aps_is_secret  BOOLEAN      NOT NULL DEFAULT false,
  aps_updated_by VARCHAR(64)  NULL,
  aps_created_at TIMESTAMPTZ  NOT NULL DEFAULT now(),
  aps_updated_at TIMESTAMPTZ  NOT NULL DEFAULT now(),
  CONSTRAINT pk_hsm_app_settings PRIMARY KEY (aps_id),
  CONSTRAINT uq_hsm_app_settings_key UNIQUE (ent_id, aps_category, aps_key)
);
CREATE INDEX idx_hsm_app_settings_ent ON hsm_app_settings (ent_id);

-- ④ 전역 참조 시드
--    sql/seed/gpc_hs_maps.sql, sql/seed/country_extensions.sql

-- ⑤ 면장리스트 import (FN-040 어댑터 실행) → hsm_hs_references / hsm_import_batches
-- ⑥ 임베딩 생성 (FN-041) → hsr_embedding upsert
```

### 5.1 적용 원칙
- **하위호환**: `hsm_hs_country_extensions`는 additive(신규 국가 추가 시 매핑 재빌드 불필요).
- **append-only**: `hsm_resolution_audits` 하드삭제 금지(POL-003).
- **인덱스**: `hsm_hs_references`에 `hsr_hs6`/`hsr_hs_code`/`hsr_source_company`/`ent_id` + 벡터 인덱스.
- **롤백**: 각 마이그레이션에 대응 down 스크립트 준비, 시드는 멱등(upsert) 작성.
