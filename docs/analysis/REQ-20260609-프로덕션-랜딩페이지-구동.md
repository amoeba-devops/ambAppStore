## 2. AS-IS 현황 분석

### 2.1 증상
```
curl https://apps.amoeba.site/      → HTTP 404 (nginx 기본 404, 153B)
curl https://stg-apps.amoeba.site/  → HTTP 200 (정상 SPA)
```
404는 업스트림이 아니라 **nginx 자체**가 반환(Server: nginx/1.22.1).

### 2.2 프로덕션 박스 (18.138.206.18 / `ssh amb-production` / ec2-user)
| 항목 | 현황 | 문제 |
|------|------|------|
| nginx conf | `/etc/nginx/conf.d/apps.amoeba.site.conf` 존재 | `root /var/www/apps_amoeba; try_files $uri $uri/ =404;` |
| 정적 루트 | `/var/www/apps_amoeba` | **디렉토리 자체가 존재하지 않음** → 모든 경로 404 |
| app-store 컨테이너 | **0개** (web-platform/bff-platform/mysql-apps 전무) | 백엔드/프론트 없음 |
| docker network | `amb-apps-network` **없음** (compose가 external로 참조) | up 시 실패 |
| 포트 3100/5200/3308 | 전부 미사용 | 충돌 없음(양호) |
| 리포 체크아웃 | **없음** | clone 필요 |
| SSL 인증서 | `/etc/nginx/ssl/amoeba.site.crt` (wildcard) 존재 | 재사용 가능 |
| 도구 | git 2.40, docker compose v2.29 (node 없음) | 빌드는 Docker 내부 → 무관 |
| 기존 컨테이너 | amb-*-production(AMA), production-web/api-1 | 포트 8080/8081/8090/3019/3020 — 무충돌 |

> 즉, 이 박스의 prod 전략은 **zero-touch**(car-v2만 Render로 프록시)였고, 플랫폼 랜딩(`/`)은 placeholder 정적 conf만 남아 한 번도 배포된 적이 없음.

### 2.3 스테이징 (정상 동작 — 참조 모델)
- 컨테이너: `web-platform`(5200), `bff-platform`(3100), `mysql-apps`(3308) + 앱별 컨테이너
- nginx: `/`→127.0.0.1:5200, `/api/`→127.0.0.1:3100, `/app-car-manager/`→5201 …
- `.env`: `JWT_SECRET`(AMA 검증), `DB_*`, `MYSQL_ROOT_PASSWORD`, `VITE_*` 존재

### 2.4 랜딩페이지 코드 의존성
- `apps/platform/frontend/src/pages/LandingPage.tsx` → `useApps()` → `GET /api/v1/apps`
- 백엔드(`bff-platform`) + MySQL(`db_app_platform.plt_apps`) 없으면 히어로 텍스트만 뜨고 카탈로그는 빈 채 → **R2 미충족**

## 3. TO-BE 요구사항

### 3.1 AS-IS → TO-BE 매핑
| 영역 | AS-IS | TO-BE |
|------|-------|-------|
| 프로덕션 컨테이너 | 없음 | `bff-platform`+`web-platform`+`mysql-apps` 구동 (스테이징 동등) |
| docker network | 없음 | `amb-apps-network` 생성 |
| nginx `/` | `root /var/www/apps_amoeba`(404) | `proxy_pass http://127.0.0.1:5200/` |
| nginx `/api/` | 없음 | `proxy_pass http://127.0.0.1:3100/api/` |
| nginx `/app-car-manager-v2/` | (prod.conf 초안) Render 프록시 | **유지** (회귀 방지) |
| DB 카탈로그 | 없음 | `init-db.sql`+`seed-apps.sql`로 5개 앱 시드 |
| 리포 | 없음 | prod 박스에 clone (`~/ambAppStore`) |
| 배포 스크립트 | staging 전용 | `deploy-production.sh` 추가(git pull origin production) |

- synchronize는 prod에서 비활성이지만 init 스크립트가 스키마+시드를 보장 → 별도 수동 SQL 불필요.
- 카탈로그 시드: 5개 앱(car-manager, hscode, sales-report, stock-management, car-manager-v2).

```
사용자 → https://apps.amoeba.site/
         │
         ▼
   nginx(443) location /  → 127.0.0.1:5200 (web-platform SPA)
         │  index.html + JS 번들 로드
         ▼
   SPA: useApps() → GET /api/v1/apps
         │
         ▼
   nginx location /api/ → 127.0.0.1:3100 (bff-platform)
         │  → mysql-apps: SELECT * FROM plt_apps
         ▼
   카탈로그 카드 5개 렌더 (랜딩 정상)

   [분기] /app-car-manager-v2/* → Render prod (기존 유지)
```

## 6. 기술 제약사항
- **무중단/회귀방지**: nginx 교체 시 기존 `/app-car-manager-v2/` Render 프록시 블록을 반드시 보존. 교체 전 `.bak` 백업, `nginx -t` 통과 후에만 reload.
- **보안**: mysql-apps 호스트 포트(3308)는 외부 노출 불필요 → 가능하면 `127.0.0.1` 바인딩 권장(후속). JWT_SECRET은 AMA와 동일해야 SSO 통과.
- **CSP**: 랜딩은 AMA 포털 iframe 내장 가능해야 함 → `frame-ancestors 'self' https://ama.amoeba.site`.
- **배포 원칙**: 본 스택은 스테이징에서 이미 검증 완료(동일 compose 구동 중) → "스테이징 먼저" 조건 충족. prod 배포는 production 브랜치 기준.
- **VITE 인라인**: `VITE_*` 변경 시 web-platform 이미지 재빌드 필수.
