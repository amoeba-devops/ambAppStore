## 1. 요구사항 요약

운행일지(Trip Log)는 한국 업무용승용차 운행기록부/베트남 세무 보고에 사용되는 법적·감사용 데이터로, 잘못 입력된 건을 안전하게 처리해야 한다. 물리적 삭제(Hard Delete)는 감사 흔적이 사라지므로 금지하며, **상태(Status)에 `VOIDED` 값을 추가**하여 "무효 처리"하는 방식으로 구현한다.

| # | 요구사항 | 유형 |
|---|---------|------|
| R-01 | `TripLogStatus` enum에 `VOIDED` 값 추가 (DB + Backend) | DB+BE |
| R-02 | `car_trip_logs` 테이블에 무효처리 audit 컬럼 4개 추가 (`ctl_voided_at`, `ctl_voided_by`, `ctl_voided_by_name`, `ctl_voided_reason`) | DB |
| R-03 | `PATCH /api/v1/trip-logs/:id/void` 엔드포인트 신설 — 사유 필수, status 가드 적용 | BE |
| R-04 | `VOIDED` 상태 trip log 는 추가 수정/제출/검증 불가 | BE |
| R-05 | 무효 처리 시 연결된 proxy `dispatch_request` 도 `CANCELLED` 로 동기화 | BE |
| R-06 | 운행일지 상세 페이지에 "무효 처리" 버튼 + 사유 입력 모달 추가 | FE |
| R-07 | `VOIDED` 상태는 목록/상세에서 시각적으로 구분 (회색 배지, 취소선) + 사유 툴팁 | FE |
| R-08 | 월간 통계(총 거리·연료비·운행수)는 `VOIDED` 제외 | FE |
| R-09 | Excel Export 에 `Voided At`, `Voided Reason` 컬럼 추가 | BE |
| R-10 | i18n 번역키 추가 (ko/en/vi 3개 언어) | i18n |

### 2.6 문제점

| # | 문제 |
|---|------|
| P-01 | 잘못 입력된 운행일지를 처리할 방법이 없다. 사용자가 실수 입력 후 수정만 가능하며, 아예 무효화하려면 운영자가 DB 직접 조작해야 함. |
| P-02 | `VERIFIED` 후에는 어떤 수정도 불가능 → 검증 후 발견된 오류를 처리할 표준 절차가 없음. |
| P-03 | Excel 내보내기 시 모든 trip log 가 포함되어, 잘못된 건을 식별할 수 없음. |
| P-04 | `proxy dispatch` (수동 등록 시 함께 생성된 `dispatch_request`) 도 같이 정리되지 않으면 dispatch 통계가 왜곡됨. |

## 3. TO-BE 요구사항

### 3.1 AS-IS → TO-BE 매핑

| 영역 | AS-IS | TO-BE |
|------|-------|-------|
| Enum | 3개 상태 | 4개 상태 (`VOIDED` 추가) |
| DB 컬럼 | audit 컬럼 없음 | `ctl_voided_at`, `ctl_voided_by`, `ctl_voided_by_name`, `ctl_voided_reason` 4개 추가 |
| API | DELETE/VOID 엔드포인트 없음 | `PATCH /api/v1/trip-logs/:id/void` 추가 |
| Service | `update`/`submit` 만 존재 | `void(entityId, id, reason, userId, userName)` 추가 |
| 상세 UI | Edit/Submit/Verify 버튼만 | "무효 처리" 버튼 + 사유 입력 모달 추가 |
| 목록 UI | 모든 상태 동일 스타일 | `VOIDED` 행은 회색·취소선·사유 툴팁 |
| 통계 | 모든 trip log 합산 | `VOIDED` 제외 합산 |
| Excel | 기본 컬럼 | `Voided At`, `Voided Reason` 컬럼 추가 |

### 3.2 신규 필드 (Backend Entity 추가분)

```typescript
@Column({ name: 'ctl_voided_at', type: 'datetime', nullable: true })
ctlVoidedAt: Date | null;

@Column({ name: 'ctl_voided_by', type: 'char', length: 36, nullable: true })
ctlVoidedBy: string | null;          // AMA user.sub

@Column({ name: 'ctl_voided_by_name', type: 'varchar', length: 100, nullable: true })
ctlVoidedByName: string | null;      // 스냅샷 (user 삭제 대비)

@Column({ name: 'ctl_voided_reason', type: 'varchar', length: 500, nullable: true })
ctlVoidedReason: string | null;      // 필수 입력 사유
```

### 3.3 신규 상태 전이 규칙

```
IN_PROGRESS ──submit──→ COMPLETED ──verify──→ VERIFIED
     │                     │
     └─────void────────────┴────void──→ VOIDED  (종료, 되돌리기 불가)

(VERIFIED 는 void 불가)
```

| 현재 상태 | Void 가능? | 비고 |
|-----------|-----------|------|
| IN_PROGRESS | ✅ | 일반적인 케이스 |
| COMPLETED | ✅ | 제출 후에도 검증 전이면 가능 |
| VERIFIED | ❌ | 이미 보고서·세무에 포함되었을 수 있음 (BusinessException `CAR-E6005`) |
| VOIDED | ❌ | 멱등성 위반 (BusinessException `CAR-E6006`) |

### 3.4 비즈니스 로직

**Backend** — `TripLogService.void(entityId, id, reason, userId, userName)`:

1. trip log 조회 (`findById` 재사용).
2. `ctlStatus === VERIFIED` → `CAR-E6005 "Cannot void verified trip log"` (HTTP 400).
3. `ctlStatus === VOIDED` → `CAR-E6006 "Trip log already voided"` (HTTP 400).
4. `reason` 비어있음 → `CAR-E6007 "Void reason is required"` (HTTP 400).
5. trip log 업데이트:
   - `ctlStatus = VOIDED`
   - `ctlVoidedAt = now()`
   - `ctlVoidedBy = userId`
   - `ctlVoidedByName = userName`
   - `ctlVoidedReason = reason`
6. 연결된 proxy dispatch (`tripLog.cdrId` 가 존재하고 `cdrIsProxy === true`)가 있으면 `DispatchStatus.CANCELLED` 로 업데이트.
7. 저장된 trip log 반환.

### 4.3 DB 마이그레이션 전략

**스테이징/프로덕션은 `synchronize: false`** 이므로 수동 SQL 필요.

```sql
-- 1) Enum 확장 (backward compatible)
ALTER TABLE car_trip_logs
  MODIFY COLUMN ctl_status ENUM('IN_PROGRESS','COMPLETED','VERIFIED','VOIDED')
    NOT NULL DEFAULT 'IN_PROGRESS';

-- 2) Audit 컬럼 4개 추가 (모두 NULL 허용)
ALTER TABLE car_trip_logs
  ADD COLUMN ctl_voided_at DATETIME NULL AFTER ctl_status,
  ADD COLUMN ctl_voided_by CHAR(36) NULL AFTER ctl_voided_at,
  ADD COLUMN ctl_voided_by_name VARCHAR(100) NULL AFTER ctl_voided_by,
  ADD COLUMN ctl_voided_reason VARCHAR(500) NULL AFTER ctl_voided_by_name;
```

- **Down migration** (롤백):
  ```sql
  UPDATE car_trip_logs SET ctl_status='COMPLETED' WHERE ctl_status='VOIDED';
  ALTER TABLE car_trip_logs
    DROP COLUMN ctl_voided_at,
    DROP COLUMN ctl_voided_by,
    DROP COLUMN ctl_voided_by_name,
    DROP COLUMN ctl_voided_reason,
    MODIFY COLUMN ctl_status ENUM('IN_PROGRESS','COMPLETED','VERIFIED') NOT NULL DEFAULT 'IN_PROGRESS';
  ```

## 5. 사용자 플로우

### 5.1 정상 무효처리 시나리오 (IN_PROGRESS → VOIDED)

```
[운전자/관리자]
  │
  ├─ 1) 운행일지 목록에서 잘못 입력된 건 클릭
  │      → 상세 페이지 진입 (status: IN_PROGRESS)
  │
  ├─ 2) [Void] 버튼 클릭
  │      → 모달 표시: "운행일지 무효 처리"
  │      → 경고문 표시: "무효 처리된 일지는 되돌릴 수 없습니다"
  │
  ├─ 3) 사유 입력 (예: "출발 마일리지 잘못 입력")
  │      → [확인] 버튼 클릭
  │
  ├─ 4) Frontend: PATCH /api/v1/trip-logs/:id/void { reason }
  │
  ├─ 5) Backend:
  │      ├─ status 검증: IN_PROGRESS 또는 COMPLETED 인가?
  │      ├─ reason 길이 검증 (5~500자)
  │      ├─ car_trip_logs 업데이트: status=VOIDED, voided_* 4 cols 기록
  │      └─ proxy dispatch 가 있으면 → CANCELLED 로 업데이트
  │
  └─ 6) 성공 토스트 + 페이지 refetch
         → status 배지: VOIDED (회색)
         → 사유·처리자·시간 표시
         → Edit 버튼 숨김
```

### 5.2 분기 시나리오

| 분기 | 조건 | 동작 |
|------|------|------|
| 분기 1 | `status === 'VERIFIED'` | "Void" 버튼 자체가 표시되지 않음 (FE) + BE 가드 (`CAR-E6005`) |
| 분기 2 | `status === 'VOIDED'` | "Void" 버튼 표시되지 않음 + BE 가드 (`CAR-E6006`) |
| 분기 3 | 사유 미입력 | FE validation 차단 (5자 미만 disable) + BE 가드 (`CAR-E6007`) |
| 분기 4 | 사유 500자 초과 | FE maxLength 500 + BE class-validator `@MaxLength(500)` |
| 분기 5 | proxy dispatch 가 이미 CANCELLED/COMPLETED | dispatch 업데이트 skip (멱등성) |

### 5.3 목록 페이지 통계 영향

```
[월간 통계 표시]
  ├─ 전체 trip log: 100건
  ├─ VOIDED: 5건
  └─ 통계 계산 대상: 95건 (VOIDED 제외)
        ├─ 총 운행수: 95건
        ├─ 총 거리: VOIDED 5건 제외한 distance 합계
        └─ 총 연료비: VOIDED 5건 제외한 fuelCost 합계
```

## 6. 기술 제약사항

### 6.1 호환성

| 항목 | 제약 |
|------|------|
| MySQL 8.0 ENUM 확장 | `ALTER TABLE ... MODIFY COLUMN ENUM(...)` 으로 값 추가는 backward compatible. 기존 row 모두 보존됨. |
| TypeORM enum sync | 스테이징/프로덕션은 `synchronize: false` → 수동 SQL 마이그레이션 후 배포해야 함. |
| 기존 trip log 데이터 | VOIDED 처리되지 않음, 모든 row 의 `ctl_voided_*` 컬럼은 NULL 로 유지 → 영향 없음. |
| Mobile (응답 호환성) | response 에 voided* 필드 추가는 기존 클라이언트가 무시하므로 안전. |

### 6.2 성능

- VOID 작업은 단일 row UPDATE + 선택적 dispatch 1건 UPDATE → 비용 미미.
- 통계 계산 시 VOIDED 제외 필터는 `Array.filter` 1회 → O(n) 영향 무시 가능.
- DB index: `ctl_status` 가 이미 enum index 로 활용되는 경우 변경 불필요. (현 시점 별도 index 없음 — 필요 시 추후 `idx_trip_logs_ent_status` 검토.)

### 6.3 보안 및 권한

| 항목 | 정책 |
|------|------|
| 인증 | `@Auth()` 적용 (기존 trip-log endpoint 와 동일) — JWT + `ent_id` 격리 |
| 권한 | 1단계: 모든 인증 사용자가 자신의 ent_id 소속 trip log void 가능. 추후 admin/manager 권한 분리 시 별도 데코레이터 추가. |
| 감사 추적 | `ctl_voided_by` (user.sub) + `ctl_voided_by_name` 스냅샷 + `ctl_voided_at` + `ctl_voided_reason` 모두 영구 기록 |
| 사유 입력 | 필수 (5자 이상 500자 이하). 빈 사유 무효처리 차단. |

### 6.4 데이터 무결성

- VOIDED 는 종료 상태이며 되돌리기(unvoid) API 는 **이번 범위에서 제공하지 않음**. 필요 시 DB 직접 조작 (감사 흔적 남기기 위해 의도적).
- proxy dispatch 동기화: trip log void 시 연결된 dispatch (`tripLog.cdrId`, `cdrIsProxy === true`)도 CANCELLED 처리하여 dispatch 통계 왜곡 방지.
- non-proxy dispatch (외부에서 만든 일반 배차)는 자동 변경하지 않음 — 별도 dispatch 취소 절차 사용.

### 6.5 회귀 위험

| # | 위험 | 대응 |
|---|------|------|
| RR-01 | 월간 통계가 VOIDED 포함하여 계산되면 보고서 왜곡 | TC 에서 통계 계산 검증, 코드 리뷰 시 필터 누락 체크 |
| RR-02 | VOIDED 상태에서 update API 가 통과되면 audit 무결성 깨짐 | service.update 에 VOIDED 가드 추가 (`CAR-E6002` 메시지에 VOIDED 도 포함) |
| RR-03 | proxy 가 아닌 dispatch 까지 CANCELLED 되면 데이터 손상 | `cdrIsProxy === true` AND `cdrStatus !== CANCELLED` 조건 명시 |
| RR-04 | Excel import 가 VOIDED row 를 다시 IN_PROGRESS 로 만들지 않는지 | 별도 row 로 생성되므로 영향 없음 (import 는 항상 신규 row 생성) — TC 확인 |
