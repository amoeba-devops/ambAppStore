# PLAN-20260601 — 프로덕션 apps.amoeba.site 앱스토어 배포 계획

> 목적: 프로덕션(`apps.amoeba.site`, 18.138.206.18 / AWS 싱가포르)에 ambAppStore 플랫폼 +
> `app-car-manager-v2`를 배포하고, AMA(`ama.amoeba.site`)에서 v2 커스텀앱 링크가 노출·로그인되도록 한다.
>
> 발단: 프로덕션 AMA `/menu/custom-apps`에 v2 링크 미노출. 원인은 ① 프로덕션 AMA DB에
> `amb_entity_custom_apps` 시드 행 부재 + ② 프로덕션 `apps.amoeba.site`에 앱스토어/v2 자체가 미배포.
> 본 계획은 ②(인프라)와 ①(데이터)을 함께 다룬다.
>
> ⚠️ 본 문서는 **계획만** 수립한다. 실제 프로덕션 변경은 별도 승인 후 진행한다.
> ⚠️ 배포 원칙: 스테이징에서 검증된 구성만 프로덕션에 반영한다 (CLAUDE.md).

### 1.3 핵심 제약사항 (스테이징과 다른 점 — 반드시 반영)

| # | 제약 | 영향 |
|---|---|---|
| C1 | **프로덕션 nginx는 호스트에서 실행** | 컨테이너 DNS명(`web-platform:80`) 사용 불가 → `proxy_pass http://127.0.0.1:<호스트포트>`로 재작성 필요 |
| C2 | **JWT_SECRET 일치 필수** | 플랫폼/v2의 `JWT_SECRET` = 프로덕션 AMA(`amb-api-production`)의 `JWT_SECRET` 와 byte-for-byte 동일해야 클릭 시 로그인. 다르면 `/session-expired` 401 |
| C3 | **v2 DB = Neon Postgres** | v2는 자체 Neon DB 사용. 프로덕션 v2가 **스테이징 Neon과 분리된 prod 브랜치**를 쓸지 결정 필요 (데이터 분리) |
| C4 | **SSL 인증서 방식 상이** | 프로덕션은 letsencrypt 아님 → 기존 `/etc/nginx/ssl/amoeba.site.crt` 재사용 (와일드카드가 apps.amoeba.site 포함하는지 확인) |
| C5 | **MySQL 신규 기동** | 프로덕션엔 MySQL 없음 → `mysql-apps` 컨테이너 + 초기화 SQL + 볼륨 필요 |
| C6 | **호스트 포트 충돌 점검** | 사용 중: 3000, 3019, 3020, 5432, 8080, 8081, 8090. 신규: 3100/5200/3308/3105 (현재 미충돌로 보이나 배포 시 재확인) |
| C7 | **CSP frame-ancestors** | v2가 AMA iframe 안에서 떠야 함 → apps.amoeba.site 응답 CSP에 `https://ama.amoeba.site` 허용 + v2 `NEXT_PUBLIC_AMA_ORIGIN`에 prod AMA 포함 |

## 2. 단계별 구현 계획

### Phase 0 — 사전 결정/검증 (코드 변경 없음)
- **Step 0.1** JWT_SECRET 정합성 결정: 프로덕션 AMA의 `JWT_SECRET` 지문 확인 → 플랫폼/v2 `.env`를 동일 값으로 설정할지, 또는 별도 prod 시크릿으로 통일할지 결정.
  └─ 사이드 임팩트: 잘못되면 전 엔티티 로그인 401. **배포 전 최우선 확인.**
- **Step 0.2** v2 prod 데이터 분리 정책 결정 (Neon prod 브랜치 신규 vs 스테이징 공유).
  └─ 사이드 임팩트: 공유 시 스테이징/프로덕션 데이터 혼선. 분리 권장.
- **Step 0.3** 프로덕션에 배포할 앱 범위 확정 (우선 platform + v2만? 또는 5개 전부).
  └─ 사이드 임팩트: 범위 클수록 포트/리소스/검증 부담 증가.

### Phase 1 — 인프라 기반
- **Step 1.1** 프로덕션 서버에 ambAppStore 체크아웃 (`production` 브랜치) 배치 경로 결정 (예: `/var/www/apps_amoeba` 또는 `~/ambAppStore`).
- **Step 1.2** `docker network create amb-apps-network` (external 네트워크 생성).
  └─ 사이드 임팩트: 기존 `production_amb-network`와 별개. AMA↔앱스토어 컨테이너 직접 통신은 nginx/HTTP 경유라 네트워크 분리 가능.
- **Step 1.3** 프로덕션 `.env` 작성: `apps/platform/.env`, `apps/app-car-manager-v2/.env`
  (DB 자격, `JWT_SECRET`(C2), `VITE_API_BASE_URL=/api`, `VITE_AMA_LOGIN_URL=https://ama.amoeba.site/login`,
  `NEXT_PUBLIC_AMA_ORIGIN=https://ama.amoeba.site`, `BASE_PATH=/app-car-manager-v2`, Neon `DATABASE_URL`).
  └─ 사이드 임팩트: VITE_*·NEXT_PUBLIC_* 는 빌드 시점 인라인 → 변경 시 이미지 재빌드 필수.

### Phase 2 — 컨테이너 빌드·기동
- **Step 2.1** `mysql-apps` 기동 + 초기화(`init-db.sql`, `seed-apps.sql`) — `plt_apps`에 `app-car-manager-v2` 포함 확인.
- **Step 2.2** `bff-platform`(3100) + `web-platform`(5200) 빌드·기동.
- **Step 2.3** `next-car-manager-v2`(3105→3001) 빌드·기동, health `/(app-car-manager-v2)/api/v1/health`.
  └─ 사이드 임팩트: 프로덕션엔 `deploy-staging.sh` 미적용 → **prod 전용 배포 절차/스크립트** 필요 (또는 스크립트 일반화). 직접 `docker compose build` 금지 원칙과 충돌하므로 prod 스크립트 정비 선행.

### Phase 3 — nginx 라우팅 (호스트 모드, C1)
- **Step 3.1** `apps.amoeba.site.conf` 신규 작성 (백업 후 교체):
  - `location / → http://127.0.0.1:5200/` (web-platform 호스트포트)
  - `location /api/ → http://127.0.0.1:3100/api/`
  - `location /app-car-manager-v2/ → http://127.0.0.1:3105` (+ `X-Forwarded-Host $host`, upgrade 헤더)
  - SSL: 기존 `/etc/nginx/ssl/amoeba.site.*` 재사용 (C4)
  - CSP: `frame-ancestors 'self' https://ama.amoeba.site` (C7)
- **Step 3.2** `nginx -t` → `systemctl reload nginx`.
  └─ 사이드 임팩트: 설정 오류 시 전체 가상호스트 영향 → 반드시 `-t` 후 reload, 백업 보관.

### Phase 4 — 데이터 시드 (① 데이터 격차 해소)
- **Step 4.1** 프로덕션 AMA Postgres(`amb-postgres-production`)에 `amb_entity_custom_apps` 시드.
  - 파일: `apps/app-car-manager-v2/scripts/seed-ama-entity-custom-app.FILLED-20260601.sql`
  - 대상 엔티티(스테이징 plt_subscriptions ACTIVE 기준): CARGO434, UIT327, DEMO, VN01
  - **eca_url 결정**: 프로덕션 배포 완료 시 `https://apps.amoeba.site/app-car-manager-v2`로 교체 (미배포 임시 단계에선 stg-apps).
  └─ 사이드 임팩트: eca_url/JWT 불일치 시 노출돼도 401. Phase 0.1·3 완료 후 prod URL로 적용.
- **Step 4.2** 프로덕션 plt_apps 카탈로그 시드(`seed-ambappstore-app.sql`)를 prod MySQL에 적용 (구독 신청 경로용).

### Phase 5 — 검증
- **Step 5.1** `curl https://apps.amoeba.site/app-car-manager-v2/api/v1/health` → `{success:true}`
- **Step 5.2** 프로덕션 AMA 로그인 → `/menu/custom-apps`에 v2 노출 확인 → 클릭 → 로그인(쿠키) → 대시보드.
- **Step 5.3** 4개 엔티티별 노출/권한(allowed_roles) 확인.

## 부록 A — 현재 vs 목표 nginx (apps.amoeba.site)

**현재 (정적):**
```nginx
server { listen 443 ssl; server_name apps.amoeba.site;
  root /var/www/apps_amoeba; location / { try_files $uri $uri/ =404; } }
```

**목표 (호스트모드 리버스 프록시, 초안):**
```nginx
server {
  listen 443 ssl; server_name apps.amoeba.site;
  ssl_certificate /etc/nginx/ssl/amoeba.site.crt;
  ssl_certificate_key /etc/nginx/ssl/amoeba.site.key;
  add_header Content-Security-Policy "frame-ancestors 'self' https://ama.amoeba.site" always;
  client_max_body_size 10M;

  location /api/ { proxy_pass http://127.0.0.1:3100/api/; include /etc/nginx/proxy_params; }
  location /app-car-manager-v2/ {
    proxy_pass http://127.0.0.1:3105;
    proxy_set_header Host $host; proxy_set_header X-Forwarded-Host $host;
    proxy_set_header X-Forwarded-Proto $scheme; proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection "upgrade";
  }
  location / { proxy_pass http://127.0.0.1:5200/; proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme; }
}
```
> 스테이징 conf 대비 차이: 컨테이너 DNS명(`web-platform:80`) → 호스트 포트(`127.0.0.1:5200`). 이유: 프로덕션 nginx는 호스트 실행(C1).
