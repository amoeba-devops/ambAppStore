# PLN-260814 — 승인된 org 사용자의 v2 앱 자동 진입 항구적 해결

- **작성일**: 2026-08-14
- **선행 문서**: [REQ-260814](../analysis/REQ-260814-승인된앱-자동진입-항구적해결.md)
- **범위**: `apps/platform/frontend` 단독 (백엔드·DB 변경 없음)

## 1. 시스템 개발 현황 분석

### 1.1 디렉토리 구조 (해당 범위)

```
apps/platform/frontend/src/
├── App.tsx                          # EntityContextInitializer 위치
├── lib/
│   ├── ama-token.ts                 # 토큰 디코드/캡처 (FIX-260813 신규)
│   └── app-launch.ts                # buildAppLaunchUrl()
├── stores/
│   ├── entity-context.store.ts      # ★ persist 대상
│   └── auth.store.ts
├── hooks/useSubscription.ts         # useEntitySubscriptions
├── pages/AppDetailPage.tsx          # ★ 핵심 분기
└── i18n/locales/{ko,en,vi}/platform.json
```

### 1.2 기술 스택

React 18 + TS5 + Zustand + React Query 5 + Vite 5. `zustand/middleware`의 `persist`는 zustand에 내장 — **신규 의존성 없음**.

### 1.3 기존 코드 상황

- `entity-context.store.ts` 는 24줄 순수 store — persist 미적용
- `ama-token.ts` 의 `initialSearch`(L35)는 모듈 로드 시점 캡처 — 이 시점을 놓치면 복구 불가
- `AppDetailPage.tsx` L60-62의 `currentStatus`가 `null` 단일 값으로 unknown/미신청을 뭉갬

### 1.4 제약사항

| # | 제약 |
|---|---|
| C1 | 구 iframe 경로 무회귀 — `from=iframe` 우선순위 유지 |
| C2 | 자동 진입은 세션당 slug 1회 (무한 루프 방지) |
| C3 | 원본 JWT persist 금지 — 식별자만 |
| C4 | `sessionStorage` 사용 (localStorage 아님) |
| C5 | 빌드 시 `tei-hscode` 정지 필요 (호스트 RAM 4.36G 피크) |

## 2. 단계별 구현 계획

### Phase 1 — 컨텍스트 영속화 (S1 제거)

**Step 1.1** `entity-context.store.ts` 에 `persist` 미들웨어 적용
- `name: 'plt-entity-ctx'`, `storage: createJSONStorage(() => sessionStorage)`
- `partialize`로 `entity`만 저장 (액션 제외)
- └─ 사이드 임팩트: store 초기값이 sessionStorage에서 하이드레이트됨. 기존 `setEntity`/`clearEntity` 시그니처 불변이므로 소비처(`App.tsx`, `AppDetailPage`, `Header`) 코드 변경 불필요.

**Step 1.2** `App.tsx` `EntityContextInitializer` — 이미 컨텍스트가 있으면 덮어쓰지 않도록 가드
- 토큰 클레임 폴백 전에 `useEntityContextStore.getState().entity` 확인
- └─ 사이드 임팩트: 없음. 쿼리 파라미터 경로는 여전히 최우선(명시적 진입이 복원값을 이김).

### Phase 2 — unknown 상태 분리 (S2/S3 가시화, R3)

**Step 2.1** `AppDetailPage.tsx` — 상태 파생 로직 수정
- `contextResolved = isAuthenticated || !!effectiveEntId` 도입
- `currentStatus`: 미해결 시 `'UNKNOWN'` 반환하도록 분기
- └─ 사이드 임팩트: **高**. 기존 최종 else("신청하기")에 도달하던 unknown 케이스가 새 분기로 이동. 진짜 미신청(`contextResolved && status===null`)은 기존대로 "신청하기" 유지 — 이 구분이 회귀 방지의 핵심.

**Step 2.2** unknown 안내 배너 + i18n 키 3종 추가
- ko/en/vi 3개 파일 동시 수정 (누락 시 키 노출)
- └─ 사이드 임팩트: 없음 (신규 키만 추가).

### Phase 3 — 자동 진입 (R1)

**Step 3.1** `AppDetailPage.tsx` — `useEffect` 자동 리다이렉트
- 조건 3종(REQ §3.2) 전부 충족 시 `window.location.href = buildAppLaunchUrl(slug)`
- 가드 키: `sessionStorage['plt-auto-entered:'+slug]`
- └─ 사이드 임팩트: **高**. 앱이 카탈로그로 되돌려보내는 경우 루프 위험 → Step 3.2로 차단.

**Step 3.2** 루프 가드 + 전환 중 UI
- 리다이렉트 직전 가드 키 기록, 이후 동일 slug 자동 진입 억제
- 리다이렉트 대기 동안 `detail.enteringApp` 표시 (빈 화면 방지)
- └─ 사이드 임팩트: 사용자가 의도적으로 카탈로그를 다시 볼 때 자동 진입이 재발동하지 않음 — 의도된 동작. 새 탭/새 세션에서는 정상 재발동.

### Phase 4 — 검증

**Step 4.1** 컨테이너 내 `tsc -b` + `vite build` (호스트에 node 툴체인 없음)
**Step 4.2** TC-260814 기반 수동 시나리오 검증
**Step 4.3** access log에 `subscriptions/entity` 요청 출현 확인 ← 핵심 지표

| 범위 | 위험도 | 설명 | 완화 |

## 6. 배포 계획

Mức 1(FIX-260813 미배포분)과 본 작업이 **같은 파일을 건드리므로 함께 배포**한다.

```bash
# 1) main PR 머지 후 프로덕션 반영
sudo docker stop tei-hscode                                   # C5: OOM 방지
sudo bash platform/scripts/deploy-staging.sh build platform
sudo docker compose --env-file .env -f docker-compose.platform.yml \
     up -d --no-deps --force-recreate web-platform            # mysql-apps 보호
sudo docker start tei-hscode
```

`deploy-staging.sh restart platform` **금지** — compose에 `mysql-apps`가 포함되어 `down` 시 동일 DB를 쓰는 앱 4개가 함께 중단된다.

## 7. 롤백

프론트엔드 번들 단독 변경이므로 이전 이미지로 `--force-recreate` 재기동하면 즉시 복구된다. DB 변경이 없어 데이터 롤백 불필요.
