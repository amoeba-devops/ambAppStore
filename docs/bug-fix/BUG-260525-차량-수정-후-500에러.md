**발견일**: 2026-05-25
**심각도**: Critical (날짜 필드 포함 수정 시 차량이 사실상 조회 불가 상태로 빠짐)
**상태**: Open
**리포트**: 사용자 — "Không thể chỉnh sửa thông tin xe"
**대상**: app-car-manager (v1) — http://localhost:5201/app-car-manager/vehicles/:id/edit

## 1. 버그 현상

- 차량 수정 페이지에서 **보험만료일** 또는 **검사일** 같은 날짜 필드를 입력 후 저장
- PATCH 호출 자체는 성공(200)이지만 직후 상세 페이지로 리다이렉트되면 화면이 빈 상태 / "데이터 없음"으로 표시됨
- 같은 차량을 새로 조회해도 동일하게 실패 → **차량이 사실상 보이지 않게 됨**
- 이후 사용자가 같은 차량을 수정하려 해도 진입 자체가 불가능 → "차량 정보를 수정할 수 없다"고 인지

> 운행일지/관제 등 다른 화면에서도 해당 차량은 상세 조회가 불가능해질 가능성이 큼.

## 2. 원인 분석

### 2.1 직접 원인 — Mapper의 잘못된 타입 가정

[apps/app-car-manager/backend/src/domain/vehicle/mapper/vehicle.mapper.ts:22-25,38](apps/app-car-manager/backend/src/domain/vehicle/mapper/vehicle.mapper.ts#L22-L25):

```typescript
dedicatedStart: entity.cvhDedicatedStart?.toISOString().split('T')[0] ?? null,
dedicatedEnd:   entity.cvhDedicatedEnd?.toISOString().split('T')[0] ?? null,
insuranceExpiry: entity.cvhInsuranceExpiry?.toISOString().split('T')[0] ?? null,
inspectionDate:  entity.cvhInspectionDate?.toISOString().split('T')[0] ?? null,
purchaseDate:    entity.cvhPurchaseDate?.toISOString().split('T')[0] ?? null,
```

엔티티 필드 타입은 `Date | null`이지만 **MySQL `date` 컬럼은 mysql2 드라이버가 기본적으로 `string`(예: `"2027-06-30"`)으로 반환**한다. 그래서 `.toISOString()`이 `undefined` → `TypeError`.

CREATE 직후 응답은 service가 `new Date(...)` 한 값을 메모리상에서 그대로 들고 있어 통과하지만, **DB에서 다시 읽어올 때(GET, PATCH 후 재조회 포함)는 string이 돌아와서 깨진다.**

### 2.2 영향 범위 — 같은 패턴이 다른 mapper에도 있음

`grep .toISOString()` 결과:

| 파일 | 라인 | 컬럼 타입 | 위험 여부 |
|------|------|----------|----------|
| `vehicle.mapper.ts` | 22, 23, 24, 25, 38 | `type: 'date'` | ❌ 모두 깨짐 |
| `driver.mapper.ts` | 14 (leaveStart), 15 (leaveEnd) | `type: 'date'` | ❌ 운전자가 휴가 시작/종료일 가지면 깨짐 |
| `maintenance.mapper.ts` | 13, 14 | `type: 'date'` | ✅ 이미 `instanceof Date` 가드 적용됨 |
| `trip-log.mapper.ts` | 16, 17, 30, 31, 32 | `datetime` | ✅ 안전 (datetime은 Date 객체) |
| `dispatch.mapper.ts` | 14, 15, 20, 41–45 | `datetime` | ✅ 안전 |
| `monitor.service.ts` | 124, 125 | `datetime` | ✅ 안전 |
| `vehicle.mapper.ts:27` (`createdAt`) | datetime | ✅ 안전 |

> mysql2의 동작: **DATE → string**, **DATETIME/TIMESTAMP → Date 객체**. `@CreateDateColumn` 등 TypeORM 데코레이터는 datetime이라 안전.

### 2.3 왜 사용자가 "수정 불가"로 인식하는가

[VehicleEditPage.tsx:83-89](apps/app-car-manager/frontend/src/pages/VehicleEditPage.tsx#L83-L89):

```typescript
await updateMutation.mutateAsync({ id, data: payload });
showToast(t('vehicle.editSaveSuccess'), 'success');
navigate(`/vehicles/${id}`);   // ← 상세 페이지로 이동
```

- PATCH는 성공 → 토스트 잠깐 뜸
- 즉시 상세 페이지로 redirect → `useVehicle(id)` → GET `/api/v1/vehicles/:id` → **500**
- VehicleDetailPage의 `isError` 분기 → "데이터 없음" 노출
- 사용자 입장: "save 했는데 차량이 사라졌다 / 수정이 안 됐다"

또한 이후 어떤 경로로 들어와도 해당 차량은 깨진 상태가 지속됨.

## 3. 수정 방안

### 3.1 안전한 날짜 직렬화 헬퍼 추가

`apps/app-car-manager/backend/src/common/utils/date.util.ts` 신규 (또는 mapper 내부 private static):

```typescript
/**
 * MySQL DATE 컬럼은 mysql2 드라이버가 string으로 반환하고, TypeORM이 save 직후 메모리에 들고
 * 있을 때는 Date 객체로 들고 있을 수 있다. 두 케이스를 모두 안전하게 'YYYY-MM-DD'로 변환한다.
 */
export function toDateString(value: Date | string | null | undefined): string | null {
  if (value == null) return null;
  if (value instanceof Date) {
    if (isNaN(value.getTime())) return null;
    return value.toISOString().slice(0, 10);
  }
  if (typeof value === 'string') {
    return value.length >= 10 ? value.slice(0, 10) : value;
  }
  return null;
}
```

### 3.2 vehicle.mapper.ts 적용

5곳 모두 헬퍼 경유로 교체:

```typescript
dedicatedStart: toDateString(entity.cvhDedicatedStart),
dedicatedEnd:   toDateString(entity.cvhDedicatedEnd),
insuranceExpiry: toDateString(entity.cvhInsuranceExpiry),
inspectionDate:  toDateString(entity.cvhInspectionDate),
// in toDetailResponse:
purchaseDate:    toDateString(entity.cvhPurchaseDate),
```

### 3.3 driver.mapper.ts 적용 (예방적)

`leaveStart`, `leaveEnd`도 같은 헬퍼 경유:

```typescript
leaveStart: toDateString(entity.cvdLeaveStart),
leaveEnd:   toDateString(entity.cvdLeaveEnd),
```

### 3.4 (선택) ColumnTransformer로 근본 해결

장기적으로는 각 `@Column({ type: 'date' })`에 ColumnTransformer를 붙여 항상 `Date` 객체로 통일하는 것도 가능. 다만 변경 폭이 넓고 마이그레이션 영향이 있어 **이번 버그 픽스에서는 mapper 레벨로만 처리**.

## 6. 재현 가능한 데이터

스테이징/프로덕션에 이미 같은 패턴으로 저장된 차량이 있다면 즉시 깨짐. 배포 후 영향을 받은 차량 ID를 audit 로그에서 추출하여 검증 권장.

로컬 재현:
```sh
# 백엔드 실행 중 가정
curl -X POST http://localhost:3101/api/v1/vehicles \
  -H "X-Entity-Id: dev-entity-001" -H "X-Entity-Code: DEV" \
  -H "Content-Type: application/json" \
  -d '{"plate_number":"DEV-PATCH-01","type":"PASSENGER","make":"Honda","model":"Civic","year":2024,"fuel_type":"GASOLINE","max_passengers":5}'
# ↑ cvhId 받아서:
curl -X PATCH http://localhost:3101/api/v1/vehicles/<cvhId> \
  -H "X-Entity-Id: dev-entity-001" -H "X-Entity-Code: DEV" \
  -H "Content-Type: application/json" \
  -d '{"insurance_expiry":"2027-06-30"}'
curl http://localhost:3101/api/v1/vehicles/<cvhId> \
  -H "X-Entity-Id: dev-entity-001" -H "X-Entity-Code: DEV"
# → 500 Internal server error (전)
# → 200 OK with insuranceExpiry: "2027-06-30" (후)
```
